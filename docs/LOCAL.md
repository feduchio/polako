# polish-local: форк под локальные модели (LM Studio)

Форк `polish` для разработки на локальных моделях (LM Studio, Mac M4 Pro, 48 ГБ). Оригинал
(`/Users/fedorsvetlov/polish`, облачные модели) не трогается. Ветка форка — `local`, remote
оригинала — `upstream`. Фаза 1 = пункты (a) и частично (c) ниже; остальное — дизайн для фазы 2.

## Исходные условия

- Одновременно в памяти умещается **одна** большая модель (17–29 ГБ при ~16 ГБ занятых системой).
  Смена модели — 10–20 с загрузки.
- Скорость: MoE Ornith 35B-A3B ≈ 500 tok/s prompt / 43–48 tok/s gen; dense 27B ≈ 110–170 / 25.
  Промпт 40–60k токенов на dense — минуты до первого токена.
- Все модели одного лайнейджа (Qwen): по правилам upstream (`inferFamily`: любой `qwen*` → `qwen`)
  это одно семейство, то есть «разнообразия вендоров» нет.

## (a) Провайдер `lmstudio` — сделано в фазе 1

`kind = "lmstudio"` в `[[providers]]` (`src/providers/lmstudio.ts`, поверх `OpenAICompatProvider`):

- `baseUrl` по умолчанию `http://localhost:1234/v1`; ключ не нужен (`apiKeyEnv` необязателен — нужен
  только если в LM Studio включён token auth).
- Стоимость 0/0; `concurrency` по умолчанию **1** (можно поднять явно, если модель загружена с `--parallel N`).
- Таймаут запроса по умолчанию **30 мин** (`timeoutMs` в конфиге). Запросы не стримятся, поэтому
  таймаут покрывает и обработку промпта, и всю генерацию.
- `listModels`: `GET /v1/models` + метаданные `lms ls --json` (`lmsPath`, по умолчанию
  `~/.lmstudio/bin/lms`, затем `PATH`). Если CLI недоступен — деградация до списка из `/v1/models`
  (тогда `supportsTools=false`: неизвестное не считается «обучено под tools»). Embedding-модели
  отфильтровываются.
- Маппинг метаданных: `trainedForToolUse` → `supportsTools`; `maxContextLength` → `contextWindow`,
  но **не больше** `contextLength` провайдера (по умолчанию 65536 = с чем модель реально грузится
  через `lms load -c`); `paramsString ≥ 20B` → tier `strong`, иначе `fast` (никогда `frontier`).
  `capabilityHints[model]` перекрывает всё (как у других провайдеров).
- LM Studio не принимает `response_format: json_object`: провайдер переписывает его в
  `json_schema` с `{type: "object"}`; strict `json_schema` проходит без изменений.
- Дубликаты `modelKey` (две кванты одной модели): побеждает первая строка `lms ls` — `lms load`
  всё равно принимает только ключ.

Пример:

```toml
[[providers]]
id = "local"
kind = "lmstudio"
timeoutMs = 1800000
contextLength = 65536
```

## (b) Планировщик резидентности модели — фаза 2

Ограничение: одна резидентная модель, загрузки никогда не пересекаются.

- Новый модуль `src/broker/residency.ts` + lane `llm.local` (ширина 1, вместо `llm.<provider>`).
  Состояние: `resident: modelKey | null`, мьютекс загрузки.
- Перед вызовом модели X: если `resident !== X` → под мьютексом `unload` (REST/`lms unload --all`)
  → `POST /api/v1/models/load {model, context_length}` (или `lms load X -c 65536 --parallel 1 --gpu max`)
  → ожидание готовности → `resident = X`. Вторая загрузка во время первой ждёт её.
- Батчинг: очередь вызовов группируется по модели; сначала выгребаются все вызовы к резидентной
  модели (с лимитом по возрасту, чтобы не было голодания), и только потом переключение. Роли
  (implementer → reviewer → council) раскладываются по фазам так, чтобы переключений было минимум.
- Состояние резидентности — наблюдаемое (событие в event log), чтобы восстановление после рестарта
  демона не делало лишнюю загрузку.
- Время загрузки идёт в бюджет времени, а не токенов.

## (c) Политика разнообразия — выбран вариант «различные fine-tune = различные семейства»

Альтернативы: (1) считать разными семействами разные fine-tune/архитектуры; (2) оставить единое
семейство `qwen` и разрешить ревьюеров из одного семейства, ужесточив детерминированные гейты.

**Выбор: (1)**, семейство = `local-<architecture>-<modelKey>` (`lmStudioFamily`). Две кванты одного
ключа — одно семейство; пользователь может склеить/развести семейства через
`capabilityHints.<model>.family`.

Почему:
- Инвариант upstream — «ответ модели не принимается там, где его может проверить модель другого
  семейства». При (2) `distinctFamilies` возвращает 1 элемент, и пул ревьюеров/судей схлопывается;
  пришлось бы править все места выбора (`composition.ts`) и семантику `reviewersPerRound` — это
  как раз «франкенштейн», которого мы избегаем. (1) работает на существующем коде без изменений.
- Фактическая независимость у разных fine-tune ниже, чем у разных вендоров, но не нулевая:
  отличаются архитектура (MoE `qwen35moe` vs dense `qwen35`), данные дообучения (coder, swift,
  abliterated), квантизация. Замеры A/B: Ornith с двумя независимыми ревьюерами прошёл 4/4 и на более сложных задачах (это не доказательство независимости, а лишь отсутствие противоположного сигнала).
- Это **псевдо-разнообразие**, и его надо компенсировать: решение о принятии кода по-прежнему
  опирается на детерминированные гейты (clean checkout, тесты, baseline-регрессии), а LLM-ревью —
  дополнение. Для режима с одной моделью (память/время) в фазе 2 добавим флаг
  `local.diversity = "distinct-finetunes" | "single-family"`; во втором режиме обязательны
  `requiredCleanRounds` ≥ upstream и усиленные гейты.

## (d) Дефолты локального режима — фаза 2

Задаются профилем `polish.local.toml` (additive, ничего не меняет в схеме upstream):

- `execution.maxParallelTasks = 1` (одна модель, одна задача).
- `candidates`: `trivial=1, normal=1, complex=2` (кандидаты идут последовательно: цена — время).
- `review.reviewersPerRound = 2` (реже 3: каждый ревьюер из другого семейства = переключение
  модели ≈ 10–20 с + время prompt processing), `council` — 2 модели + судья из резидентной.
- Бюджет рассуждений: короткий `reasoning`-бюджет для ревью/скоринга, длинный для implementer;
  провайдер сейчас передаёт поле `reasoning` как есть (OpenRouter-диалект) — для LM Studio нужно
  проверить, какой параметр реально управляет thinking, и замапить в `adaptPayload`.
- `lanes."llm.default"` не используется для `local`; `local.test`/`local.build` оставить как есть,
  но не запускать тяжёлые сборки параллельно с инференсом (память).
- Длинные таймауты и запрет `maxAttemptTokens`-ретраев на таймаут prompt processing.

## (e) Гибрид — фаза 2

Если в `secrets.env` есть ключ облачного провайдера с бесплатной моделью, брокер добавляет её
как **ревьюера другого вендора** (настоящее разнообразие, не нагружает память). Реализация:
обычный `[[providers]]` с cloud-kind рядом с `lmstudio`; нужно лишь правило роутинга «implementer =
local, минимум один ревьюер/судья из чужого семейства, если доступен» и учёт квоты бесплатного
тира. Код в основном — конфиг + небольшая правка выбора в `composition.ts`.

## (f) Что остаётся идентичным upstream (чтобы мерж upstream был лёгким)

- Весь движок, FSM, event store, гейты, council, ревью-логика — без изменений.
- Изменения upstream-файлов в фазе 1 минимальны и аддитивны:
  `src/domain/config.ts` (+kind `lmstudio`, +опциональные `timeoutMs`, `contextLength`, `lmsPath`),
  `src/providers/factory.ts` (+1 `case`, +`timeoutMs` из конфига),
  `src/providers/openaiCompat.ts` (+kind в union, +опциональный хук `adaptPayload`),
  `src/providers/index.ts` (+экспорты), `src/daemon/composition.ts` (+ветка `lmstudio` без ключа в
  `loadConfiguredProviders`).
- Всё остальное — новые файлы: `src/providers/lmstudio.ts`, тесты `lmstudio.test.ts`,
  `daemon/lmstudioConfig.test.ts`, этот документ. Планировщик резидентности и профиль дефолтов
  тоже делаются новыми файлами (`src/broker/residency.ts`, `polish.local.toml`).
- Синхронизация: `git fetch upstream && git merge upstream/<ветка>` в `local`.

## Непроверено (ждёт живого LM Studio)

Сервер LM Studio при создании форка не был запущен, поэтому живой прогон не делался: поведение
`json_object → json_schema`, формат `/v1/models` и реальные тайминги проверены только по документации
и фейковому `fetch`.

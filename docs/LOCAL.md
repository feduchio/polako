# polako: форк polish под локальные модели (LM Studio)

`polako` — форк оригинального `polish` для разработки на локальных моделях (LM Studio, Mac M4 Pro, 48 ГБ).
Оригинал (`/Users/fedorsvetlov/polish`, облачные модели) не затрагивается: у форка другие бинарники, домашний
каталог и git-пространства имён, поэтому оба инструмента можно держать установленными одновременно.
Remotes: `origin` — polako, `upstream` — оригинал. Рабочая ветка — `main`.

## Исходные условия

- В памяти умещается **одна** большая модель (17–29 ГБ при ~16 ГБ занятых системой). Смена модели — 10–20 с.
- Скорость: MoE Ornith 35B-A3B ≈ 500 tok/s prompt / 43–48 tok/s gen; dense 27B ≈ 110–170 / 25. Промпт на
  40–60k токенов у dense — минуты до первого токена.
- Все установленные модели — Qwen-лайнейдж (Ornith, Swift, Huihui, Splash); докачиваются gpt-oss, Gemma, Granite.

## Как запускать

**1. Установка (один раз и после обновления):** `pnpm cli:link` собирает проект и кладёт `polako`, `polakod`, `polako-mcp` в глобальный
каталог pnpm или (если `pnpm bin -g` пуст) в `~/.local/bin` симлинками. Установленный `polish` не затрагивается: другие имена, другой
пакет (`polako`), другой дом (`~/.polako`, `POLAKO_HOME`). Проверено на изолированном `HOME`: рядом лежащий `polish` остался как был.
Убрать: `pnpm cli:unlink`. Если `polako` не находится — добавьте `~/.local/bin` в `PATH`.

**2. Карточки.** Формат — как в td (`docs/agents/tasks/N03-….md`): шапка, пустая строка, тело, абзац `Accept:`.

```
id: N03
title: Placement rules
depends: N02
files: domain/placement/*.ts

Что сделать и почему.

Accept: тесты на каждую причину отказа; успешная проверка не меняет кошелёк.
```

- `depends:` — id карточек через запятую; неизвестный id и цикл — ошибка **до** старта (`polako run` ничего не создаёт).
- `files:` — глобы разрешённой записи (`*` внутри каталога, `**` через каталоги, как в td). Любой изменённый файл вне списка
  отклоняет кандидата детерминированным гейтом (`scope_violation`), независимо от тестов.
- `Accept:` — критерии (абзац делится по `;`, либо список `- …`, либо раздел `## Acceptance`); они идут и воркеру, и ревьюерам
  как требования, и в проверки движка (литеральный `*.test.ts` из `files:` должен существовать и проходить).
- Необязательно: `Notes:` / `## Notes`.

**3. Запуск.**

```bash
polako run ~/td/docs/agents/tasks                         # все карточки каталога (проект = git-репозиторий карточек)
cd ~/td && polako run "docs/agents/tasks/N0*.md"           # glob (пути относительно текущего каталога)
polako run ~/td/docs/agents/tasks/N03-placement-rules.md  # одна карточка
polako run ~/td/docs/agents/tasks --only N01,N02 --brief ~/td/docs/agents/night-brief.md --detach
polako run ~/td/docs/agents/tasks --dry-run               # только проверить карточки и показать DAG; демон не нужен
```

Путь к существующему `.md`-файлу, каталогу с карточками (без `.git`) или glob по `.md` — карточки; иначе работает прежний
`polako run [project] [--mission "…"]`. `--only` берёт подмножество (зависимость от невыбранной карточки снимается и записывается в
событие: считается, что она уже в коде). Модель-оркестратор не участвует: интерпретация и DAG строятся прямо из карточек
(requirement на карточку, `depends` → рёбра), декомпозиции миссии нет; baseline, гейты, ревью, сходимость — прежние.

**Бриф и заметки под модель.** `--brief файл` (или `[cards] brief = "docs/agents/night-brief.md"` в `polako.toml`, путь от проекта)
замораживается в запуске и добавляется каждому воркеру. Заметки под модель:

```toml
[cards]
brief = "docs/agents/night-brief.md"
[cards.modelNotes]
ornith = "docs/agents/model-notes/ornith.md"   # ключ: модель целиком, начало ключа модели, или лайнейдж (qwen)
```

**4. Наблюдение.** `polako watch <run>`, `polako status <run>` (раздел CARDS: по строке на карточку — результат, коммит, минуты,
секунды смены модели, независимость ревью, кто отклонил и первая претензия), `polako log <run> -f`, `polako pause|resume|stop <run>`,
`polako answer <run> "…"` при NEEDS_HUMAN.

**5. Результат.** Работа идёт в ветке запуска `polako/<run>/run` (коммиты карточек: `polako: card N03 candidate …`); рабочее дерево
проекта не трогается. После DONE: `polako diff <run>` и `polako apply <run>` (fast-forward текущей ветки проекта; нужна чистая
рабочая копия и та же ветка, с которой начинали). Итоговый отчёт с таблицей карточек — `~/.polako/runs/<run>/report.md`. Карточка,
упавшая 5 раз, — `failed`; зависящие от неё — `skipped`; независимые идут дальше, запуск в итоге заканчивается FAILED с причиной.

Ограничения: независимость ревью в таблице берётся из ревью, покрывшего чекпоинт карточки (или первого более позднего
проверенного чекпоинта, если свой не ревьюился); смена модели считается по окну времени карточки; MCP-инструмент `run` карточки пока не принимает.


## 2. Провайдер `lmstudio`

OpenAI-совместимый клиент на `OpenAICompatProvider`: `http://localhost:1234/v1`, без ключа, стоимость 0/0,
таймаут 30 мин (запросы не стримятся), `json_object` переписывается в `json_schema` (LM Studio его не принимает).

Список моделей — `GET /v1/models` **плюс** `lms ls --json`; в список попадают **только** строки, чей `modelKey`
есть в `lms ls` с `type: "llm"`. Алиасы загруженных инстансов (`--identifier night`) и не-LLM (`phonon-…`,
embeddings) отбрасываются. Если `lms` недоступен — деградация до `/v1/models` без embedding-моделей, `supportsTools=false`.
Метаданные: `trainedForToolUse` → `supportsTools`; `maxContextLength` ограничивается `contextLength` (с чем модель реально
грузится); ≥20B → tier `strong`, иначе `fast`; никогда `frontier`. `capabilityHints` перекрывает всё.

## 3. Разнообразие: лайнейдж, а не fine-tune

Семейство локальной модели — вендор базовых весов (`localLineage`: архитектура → имя → сама архитектура → `unknown`):

| Признак | Семейство |
| --- | --- |
| `qwen*`, ornith, swift, huihui | `qwen` |
| `gpt-oss` | `openai` |
| `gemma*` | `google` |
| `granite*` | `ibm` |
| `llama*` | `meta` |
| `mistral*`, `mixtral`, `devstral`, … | `mistralai` |
| прочее | имя архитектуры; ничего не известно → `unknown` |

Два fine-tune Qwen — **одно** семейство (общие слепые зоны). Семейства совпадают с облачными (`gemma` → `google`), поэтому в гибриде
облачный Gemini и локальная Gemma считаются одним лайнейджем. `capabilityHints.<model>.family` — ручной override.

Существующие правила upstream работают без изменений: ревьюер не из семейства автора (`authorFamilies`), по одному семейству на ось
(`distinctFamilies`), роутер даёт бонус за `avoidFamilies`. Пока установлена хоть одна модель другого лайнейджа, ревью идёт на ней.

## 4. Same-model fallback с семантической изоляцией

Включается `review.sameModelFallback = true` (по умолчанию `false` в upstream-режиме, `true` в локальном профиле). Срабатывает, только когда
других лайнейджей не хватает на все оси раунда.

**Порядок выбора ревьюера на ось:** (1) модель другого лайнейджа, ещё не отвечавшая в раунде; (2) иначе лайнейдж автора **в изоляции**:
сначала *другой* fine-tune того же лайнейджа (другие веса), и только потом сама модель автора. Раунд, где был хоть один изолированный
ревьюер, помечается `same-model-isolated`, иначе `lineage`.

**Что изолировано** (проверено тестом `review-isolation.test.ts`):
- Контекст: каждый вызов — новый запрос из двух сообщений (system + user). В user — только «доверенный контекст» движка
  (цели/требования/ограничения миссии, имена и статусы проверок движка, счётчики тестов, пройденные сценарии) и diff чекпоинта
  с метаданными. **Нет**: рассуждений, отчёта и истории чата воркера, заметок кандидата.
- Протокол и system-prompt: преамбула «ты не писал этот код, он создан моделью твоего лайнейджа, презумпция ошибки» + обычный
  промпт оси + тело `reviewer-adversarial` (существующий протокол).
- Сэмплинг: `review.isolatedTemperature` = 0.7 (обычные ревьюеры — 0).
- Канарейка засеянного дефекта (R2) обязана быть пройдена этой моделью, иначе нет чистого раунда.
- **Сходимость:** при `same-model-isolated` DONE невозможен без детерминированных гейтов: на текущем чекпоинте ≥1 гейт `pass`,
  ни один не `fail/error/timeout`, `testsFailed = 0`. Иначе `NEEDS_HUMAN` («не сходимся только на вердиктах модели»).
- Запись: `ReviewExecution.independence`, событие `review.independence` на раунд, строка `reviewIndependence: …` в финальном отчёте
  (с пометкой, что гарантия слабее).

**Что НЕ изолировано** (честно):
- Одни и те же веса, если модель одна: общие слепые зоны и коррелированные ошибки промптом/температурой не убираются. Ревьюер
  вероятнее всего пропустит тот же класс дефектов, который внёс автор. Поэтому гейты обязательны, а не опциональны.
- Текст, написанный автором и попавший в diff (комментарии, имена, сообщения), ревьюер видит — он помечен как недоверенные данные.
- Дебаты (prosecutor/defender/judge) требуют трёх разных моделей и трёх семейств; при нехватке дебат пропускается и блокирующий
  UNCERTAIN-finding уходит в investigation-задачу (поведение upstream). Дебата «одна модель в трёх ролях» нет.
- Планировщик/совет, верификатор кандидатов, evidence-воркер находок не знают про изоляцию.
- Кэш промпта сервера общий; он не переносит смысл между запросами с разным system-prompt, но формально это один процесс.

## 5. Планировщик резидентности (`manageResidency`)

`ResidencyScheduler`: один вызов за раз, одна резидентная модель; очередь выбирает **сначала вызовы резидентной модели**
(до `maxBatch`=32 подряд или пока старейший вызов не ждёт `maxWaitMs`=10 мин), затем смена. Смена = `lms unload` лишних → `lms load <key> -c 65536
--parallel 1 --gpu max --identifier <key> -y`; две загрузки одновременно невозможны (одна очередь, `unloadAll` — барьер). Если нужная модель уже
загружена под алиасом (`night`), используется алиас, без перезагрузки. Раз в 30 с (и после ошибки) состояние перечитывается из `lms ps --json`.
Ширина lane у провайдера = 4, чтобы планировщик видел очередь и мог батчить; реально выполняется один вызов. Замена модели между
implementer и reviewer на задачу допустима, на вызов — избегается батчингом. Включено в локальном профиле; **выгружает всё лишнее**, поэтому
выключайте (`manageResidency = false`), если LM Studio используется параллельно вручную.

## 6. Локальный профиль

`profile = "auto"` (по умолчанию): если все включённые провайдеры — `lmstudio`, под значения пользователя подкладываются дефолты
(`src/domain/localProfile.ts`; что написал пользователь — побеждает; смешанный/облачный конфиг остаётся ровно как в upstream):
`maxParallelTasks 1`; кандидаты 1/1/2; `reviewersPerRound 2`; `sameModelFallback true`; `review.maxOutputTokens 4096` (reasoning-модель
тратит часть токенов на мысли); `contextBudget.maxPackTokens 24000`; lanes по 1; совет — 1 попытка на модель; у `lmstudio`-провайдеров
`manageResidency`, `timeoutMs` 30 мин, `contextLength` 65536. `profile = "local" | "cloud"` форсирует режим.

## 7. Гибрид — не сделан

Облачный провайдер рядом с `lmstudio` работает с upstream-правилами (профиль `auto` не применяется к смешанному конфигу; `profile = "local"`
применяет). Бесплатный облачный ревьюер как настоящий «другой лайнейдж» автоматически не подбирается — только через обычный выбор роутера.

## 8. Что остаётся идентичным upstream

Движок, FSM, event store, гейты, совет, логика ревью — без изменений в поведении при `sameModelFallback = false` и облачных провайдерах.
Изменения upstream-файлов аддитивны (опциональные поля схем, один `case`, ветка в `loadConfiguredProviders`, `reviewerCandidates` вместо
`nextUsableReviewer` с тем же порядком при пустом `isolatedFamilies`). Имена централизованы в `src/shared/brand.ts`. Синхронизация:
`git fetch upstream && git merge upstream/<ветка>`; ожидаемые конфликты — только места вызова `BRAND`.

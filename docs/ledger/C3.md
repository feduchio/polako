## MISSION_CRITICAL

1. **Adapter boundary.** The orchestrator (Node/TS) never imports Python as runtime. All llm-as-a-verifier use goes through `VerifierAdapter` (process sidecar). No other module may spawn `llm-verifier` or call `llm_verifier` APIs directly.
2. **TS fallback.** Sidecar crash, timeout, protocol error, unhealthy after one clean restart, or missing Python/package ⇒ comparison falls back to the existing TypeScript `PairwiseJudge` / deterministic pairwise path so candidate selection remains available. Fallback must not invent a winner from failed-gate candidates.
3. **Deterministic-first.** C3 must not send failed-gate candidates to the sidecar. Deterministic evidence-vector dominance still wins before any sidecar/PPT opinion (`selectTournamentWinner` contract from B3).
4. **No self-acceptance.** The new Python llm-as-a-verifier implementation must **not** be used as acceptance evidence for C3 itself.
5. **Cost / secrets.** Sidecar must not bypass Polish `routing.costEligibility` (currently `free_only` for dynamic workers/reviewers/verifiers) or write secrets into the repo. Default/test paths use an **injected/scripted client** (the `llm_verifier` `client=` hook or an equivalent protocol stub). C3 acceptance must not require live Vertex / paid OpenRouter / paid Gemini calls. Pinned Supervisor Council remains a separate user authorization and is not a sidecar verifier pin unless the user later says so.
6. **Anti-fake sidecar.** A Python process that only reimplements TS heuristic scores (`checksPassed` / `newFailures` / `linesChanged`) is **not** C3, even if it speaks JSON-lines.

## PHASE_REQUIRED

1. **Real package.** Sidecar uses PyPI `llm-verifier` (`llm_verifier.select` / `compare` / equivalent public API, currently 0.2.0). Document how the sidecar environment is created (venv or pinned requirements next to the sidecar). Missing package ⇒ health fail ⇒ TS fallback, not orchestrator crash.
2. **JSON-lines stdio protocol.** Persistent child process. Correlated request ids. `health` and scoring/selection ops. Timeouts. One clean restart on failure, then fallback. Adapter health-checks after restart.
3. **Criteria decomposition.** `VerifierAdapter` decomposes task description + acceptance criteria into sidecar criteria (bounded, non-empty defaults). Criteria are passed into `llm_verifier` `criteria=` (or protocol equivalent), not discarded.
4. **PPT.** For a non-dominated frontier of N≥2 candidates, ranking uses llm-verifier **Probabilistic Pivot Tournament** (`select`, O(Nk) pivots), not “TS swiss renamed PPT”. `config.verifier.pivotTournamentFrom` / `repeats` / `granularity` remain the strategy knobs (ADR-0001). Deterministic single-frontier winner still skips PPT.
5. **Two-stage logprob scheme.** When the configured verifier model withholds token-level logprobs, the sidecar implements the documented two-stage pipeline: closed model supplies domain reasoning + draft score; open verifier supplies `<score_A>`/`<score_B>` logprobs; reward is the expectation over the open verifier’s logits. When the verifier already exposes logprobs, skip the workaround. Fixture/scripted tests must cover both branches. Live frontier models are not required for acceptance.
6. **Production COMPARING.** `installProductionDrivers` / `createComparingDriver` must honor `config.verifier.backend`. `sidecar` uses `VerifierAdapter` (with TS fallback). `ts` keeps the B3 TypeScript judge. Default: `sidecar` with automatic TS fallback so offline/scripted runs still compare. Provenance (`candidate.compared` / rationale artifact) must record backend used, fallback-or-not, PPT vs deterministic method, and pairwise/select evidence — reconstructible without implementer transcripts.
7. **Tests (deterministic).** See acceptance checks below. They must exercise a **real Python child** for protocol/health/restart, and **scripted/fixture verifier clients** for PPT + two-stage. They must not depend on network or paid APIs.

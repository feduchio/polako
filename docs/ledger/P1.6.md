# P1.6 — Runtime mode `off` early return

**Status:** FROZEN, revision 1. **Base:** HOST `b58621a` on `phase-c-collab`.
**Plan reference:** `docs/PLAN.md` §3 P1.6. **Goal served:** G2. Closes finding 16.
**Process:** `docs/BVP.md` Process v2. Touches a production file → **two reviewers of different
families**, neither Claude.

## The defect

`corpusRuntimeEvidenceAllowsDone` (`src/domain/acceptance.ts:121-135`) is the CONVERGENCE_CHECK view
of persisted runtime evidence. Its two siblings both open with an `off` early return —
`runtimeAllowsDone` at `:86` and `runtimeCorpusAllowsDone` at `:107`. This one does not. Its body is:

```
if (mode === "required") { ... }
if (current.some((evidence) => evidence.status === "failed")) return false;
return current.length === 0 || current.some((e) => runtimeAllowsDone(mode, e, checkpointHash));
```

With `mode === "off"` the first branch is skipped, so control reaches the `failed` test, which is
written for `auto`. The divergence from the siblings is therefore **exactly one input class**: mode
`off` with at least one corpus entry whose `runtimeEvidence.checkpointHash` equals the checkpoint
under consideration and whose `status` is `"failed"`. Every other `off` input already returns `true`,
because the tail delegates to `runtimeAllowsDone`, which does have the early return. Stating the class
precisely matters: a reviewer checking "does `off` now return `true`" against any other input would
be observing behaviour that was already correct before the change.

## Why it is a production defect and not a latent one

`corpusRuntimeEvidenceAllowsDone` is reached in production through
`runtimeEvidenceAllowsDone` (`src/engine/convergenceDrivers.ts:440-446`), which has two call sites:

- `acceptedB6Done` (`:182-185`) — returns `false` before the convergence decision is even consulted;
- `b6ContinueOrRecover` (`:379-381`) — returns `{ nextPhase: "REVIEWING" }` when it is `false`.

So in mode `off` a single failed current-hash runtime entry sends the run back to `REVIEWING` on every
tick and it can never reach `DONE`, even though the operator asked for runtime validation to be off.
`off` is the mode used by `polish run --runtime off`, which is the discovery-smoke path in P2.3.

## Mandatory clauses

**MC1 — the early return is the siblings' early return, placed first.** Add `if (mode === "off") return
true;` as the **first** statement of `corpusRuntimeEvidenceAllowsDone`, before `evidences` is computed.
Not a widened `required` branch, not an extra disjunct in the tail, not a filter over `evidences`. The
clause is about the shape, because the point of the item is that the three functions should be
uniform: a reader comparing `:86`, `:107` and `:121` must see the same first line.

**MC2 — no other behaviour changes.** `required` and `auto` must be bit-for-bit unchanged for every
input, including the stale-evidence and empty-corpus cases. The four existing `required` assertions and
four existing `auto` assertions in `src/domain/runtimePolicy.test.ts:88-100` must pass unmodified; a
change to any of them is a contract violation, not an adaptation.

**MC3 — no caller changes.** `src/engine/convergenceDrivers.ts` is not edited. The defect is in the
domain helper and is fixed there. Pushing an `off` test up into the driver would leave the helper
wrong for any future caller.

**MC4 — no new exported symbol, no new config field, no new event type.** This item is one line of
production code. A helper extracted to "share" the early return between the three functions is out of
scope: it would rewrite two correct functions to fix a third.

## Acceptance criteria

**AC1** `corpusRuntimeEvidenceAllowsDone("off", corpus({ status: "failed", hash: A }), A)` is `true`.
This is the input class named above and it is `false` at base. It is the only assertion that
discriminates the fix from the defect at the domain level.

**AC2** The same, with a *mixture*: a corpus holding one `failed` current-hash entry **and** one
`passed` current-hash entry is `true` under `off`. At base this is also `false`, because the `failed`
test short-circuits before the tail's `some`. Included because an implementation that "fixed" the bug
by reordering the last two statements rather than adding the early return would pass AC1 and fail
this.

**AC3** `off` with a failed entry whose hash is **not** the checkpoint under consideration is `true`,
and `off` with an empty corpus is `true`. Both hold at base; they are asserted so that MC1's "return
before computing `evidences`" cannot regress them.

**AC4 — production observation, not a domain unit test.** Through `runtimeEvidenceAllowsDone`'s
production path: a run in mode `off` whose mission corpus holds a `failed` runtime entry at the run's
current checkpoint hash is **not** forced back to `REVIEWING` by that entry. This is the criterion that
distinguishes a fixed helper from a fixed *product*: MC3 forbids touching the driver, so the only way
AC4 can pass is if the helper is what the driver reads.

**AC5 — the parity is asserted, not assumed.** One check drives all three functions over the same
`off` inputs — `runtimeAllowsDone`, `runtimeCorpusAllowsDone` and `corpusRuntimeEvidenceAllowsDone` —
with a failed current-hash evidence, and asserts all three return `true`. This is the check that would
have caught the original omission, and it is the one that keeps the three in step when a fourth view is
added.

**AC6 — `required` and `auto` are pinned by mutation, not by inspection.** Replacing the added line
with `if (mode === "off") return false;` must fail AC1, AC2, AC3, AC4 and AC5; replacing it with
`if (mode !== "required") return true;` must fail an existing `auto` assertion. Both mutants are run
and their failures recorded in the run ledger. Per P1.1 and P1.2, mutation is how vacuity was found
both times; reading was not sufficient either time.

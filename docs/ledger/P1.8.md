## The invariant this repairs

`docs/PLAN.md` §7 lists *"Mission Acceptance Corpus cumulative and first-class"* as an
architectural invariant and marks it **violated in production today**. This item is the plan's
answer to the council's fatal objection across two rounds, and both reviewers converged on the
same fix independently.

## The defect, traced

1. `createGateDeps` (`src/engine/candidateDrivers.ts:785-787`) takes a corpus-aware callback whose
   two branches are **identical**:

   ```ts
   materializeAcceptance: (checkoutDir, artifacts, corpus) => {
     if (corpus === undefined) ctx.store.acceptance.materialize(checkoutDir, artifacts);
     else ctx.store.acceptance.materialize(checkoutDir, artifacts);
   },
   ```

   `verifyAcceptance` at `:789` drops the corpus argument too. `checkRunner` threads
   `acceptanceCorpus` into both callbacks (`src/project/checkRunner.ts:700-716`) and into
   `inspectProtectedPaths`, so the plumbing exists up to the point where it is discarded.
2. `CorpusEntry` (`src/domain/acceptance.ts:137-150`) carries `artifactHashes: Sha256[]` and **no
   `relativePath`**, while `AcceptanceStorage.materialize` (`src/store/acceptance.ts:31-38`)
   requires `{relativePath, sha256}`. A corpus entry cannot be materialized even if it reached the
   call.
3. Admission copies hashes from validation evidence
   (`src/findings/validator.ts:141-149`: `artifactHashes: validation.evidenceRefs.map(...)`), which
   are command-output blobs (`src/findings/reproduce.ts:170`), not executable files.
4. Protected-path inspection (`src/project/checkRunner.ts:650-669`) and canonical verification
   (`:700-716`) look only at `AcceptanceArtifact[]`.

Net effect: a corpus entry is metadata. It is never injected and never executed for a later
candidate, so the corpus is not cumulative and not first-class.

## Mandatory clauses (from the plan, one path, no fork)

**MC1 — where the bytes come from.** The artifact is the **winning candidate's own regression test
file** for the fixing task, read from the integration workspace **after that task passes
integration gates**. Not `validation.evidenceRefs`, which are command-output blobs; not
`suggestedCheck`, which is prose or a command (`src/findings/reproduce.ts:196-204`).
`relativePath` is that file's path relative to the repository root; `sha256` is its content hash.
**If the fixing task's diff contains no test file, no corpus artifact is admitted** and the entry
stays metadata — recorded as that outcome, never synthesised.

**MC2 — persisted as an `AcceptanceArtifact`.** Each executable corpus artifact is stored with
`relativePath` and `sha256`, through `AcceptanceStorage.putContent`. The corpus entry stores that
**artifact's id and path**, not evidence-output hashes.

**MC3 — admitted after integration, atomically with the entry.** The descriptor and the corpus
entry are appended together, after the fixing task passes integration gates.

**MC4 — the union, and it feeds all three stages.** `materializeAcceptance` and `verifyAcceptance`
**union** `acceptance.forTask` with the mission corpus artifacts, and that union feeds
(a) pre-materialization protected-path inspection, (b) materialization, and (c)
post-materialization canonical hash verification. The dead branch at `:785-787` goes.

**MC5 — no backfill, fail closed.** Legacy hash-only entries stay metadata and are recorded as
such. Any legacy entry that cannot be mapped to a path fails the gate with an explicit
`unmappable_legacy_corpus_entry`, never a silent skip.

## Acceptance criteria

**AC1 — a corpus artifact admitted for task A is executed for task B.** It is materialized into
the evaluation checkout of a later candidate for a **different** task, is protected, is
hash-verified, and **runs** — the criterion asserts the check actually executed it, not that the
file is present.

**AC2 — tampering fails the gate.** A candidate that edits the materialized corpus file fails
with a protected-path problem naming that path.

**AC3 — a legacy hash-only entry fails explicitly.** `unmappable_legacy_corpus_entry`, with the
entry id, and the gate does not pass.

**AC4 — no test file, no artifact.** A fixing task whose diff contains no test file admits no
corpus artifact, and the entry is recorded as metadata with that reason.

**AC5 — the union is a union.** With both a task artifact and a corpus artifact present, all three
stages see **both**. Asserted by iterating the stages, not by naming one.

**AC6 — atomicity.** A failure between the descriptor and the entry leaves neither.

**AC7 — mutation.** Each must fail a named check: restoring the identical two-branch callback;
dropping the corpus from `verifyAcceptance` only; dropping it from materialization only; dropping
it from canonical verification only; admitting an evidence-blob hash as the artifact; admitting
before integration; treating a legacy entry as a silent skip.

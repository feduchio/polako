18. Worker tool-loop replays the whole transcript, so cumulative token cost is quadratic in turns and pre-empts the contracted `agent.maxTurns` bound. `AgentRunner.runLoop` sends `messages: [...messages]` on every call (`src/agents/runner.ts:71`) after appending the assistant message (`:89`) and every tool result (`:122`), charges the entire prompt against one cumulative counter (`totalTokens += inputTokens + outputTokens`, `:90`), and passes the remainder as that call's output cap (`remainingTokens`, `:66`). Turn capacity therefore grows as the square root of the token budget, not linearly, and the per-call generation allowance shrinks monotonically as the transcript grows. Two consequences at production defaults (`agent.maxTurns` 32, `src/domain/config.ts:92`; `maxTaskTokens` null → `32_000`, `src/daemon/composition.ts:455`): the token budget binds well before the contracted turn count, so the `agent.maxTurns` knob accepted in `docs/ledger/B-bootstrap-discovery.md` is not the effective bound; and exhaustion returns `BUDGET_EXCEEDED` → `status: "failed"` (`src/agents/runner.ts:277-282`), so candidates can drop out of `COMPARING` by transcript length rather than by evidence, biasing the tournament frontier. `read` output is the dominant growth term and is never evicted, so re-reading one file duplicates it in context for the remainder of the loop. **Measured 2026-09-10** over the 6 `agent_transcript` artifacts in `~/.polish/artifacts` (fixture runs, two `:free` models, default 32_000 cap), corroborated by the 83 recorded worker requests whose `messages` array grows monotonically from 1 to 35 entries and from 209 to ~15,100 serialized characters inside a single loop. Resent history is **61.6–72.7% of all input tokens (mean 66.9%)**. Loops ran 10–18 turns (mean 14.2) and **none reached `agent.maxTurns` = 32**; 3 of 6 ended `BUDGET_EXCEEDED` at 32.4k–34.4k total tokens. Holding the 32_000 cap fixed, a flat prompt projects to 2.3× the turns at zero state overhead, 1.5× at a 500-token state block, 1.1× at 1,000 and **0.9× — a regression — at 1,500**, with break-even near 1,250. **The state schema budget is therefore a first-class acceptance criterion, not an implementation detail:** a verbose or unbounded schema makes this change actively worse at current task sizes, and the contract must cap it (the paper's reusable CTF schema is 5 fields). The shrinking per-call output allowance is live but not yet shown to truncate — the lowest final-call allowance observed was 618 tokens, in a transcript that had produced a 578-token output earlier. Sample is thin (N=6, one fixture, two small free models); the projection is a turn-count model only and ignores the paper's noise-robustness and state-recovery effects, which this data cannot measure. Reference architecture: SKILL.state (arXiv 2608.26263), bounded `(P, Σ_t, O_t)` prompt with the reasoning trace discarded after a runtime-validated state patch. That paper's stated auditing limitation does not apply here: `persistResult` already archives the full transcript to CAS (`src/agents/runner.ts:246-251`), so Polish can drop history from the context window while keeping it in the event log. Found while evaluating arXiv 2608.26263 against the tree. **Scheduled 2026-09-10** into the pause block after finding 19 and before items 11–15; contract not yet drafted. **Baseline moved 2026-09-12 by items 9+19, and the projection must be re-derived against the new one, not the old.** A production worker's first request was `task.description` alone; it is now a composed pack, and the pack is resent every turn exactly as the transcript is. Measured on the merged base with the derived cap of 1,333 tokens at production defaults: a small task goes from 10 to 519 estimated tokens, a self-host-scale task with a 269-token description and six acceptance clauses goes from 269 to 879. The pack is therefore a permanent per-turn constant of roughly 520-880 tokens, against the ~1,250-token break-even this finding measured for such a constant. Most of that headroom is now spent before finding 18 is drafted, so its state block competes with the pack rather than with an empty prompt, and the 2.3x / 1.5x / 1.1x / 0.9x projection no longer describes the tree. Stated as the cost it actually is: the pack does not overrun the budget -- `runLoop` stops at `totalTokens < maxTokens` -- it **displaces turns**. Calibrated against this finding's own measurements (14.2 mean turns, quadratic history growth against a 32,000 cap), a 519-token pack costs roughly 11% of a run's worker turns and an 879-token one roughly 17%. Ordering rationale and the measurement prerequisite are in *Prompt-path ordering constraints*, `docs/ledger/PHASE-C.md`.

Not a regression: `task.description` was a production worker's entire unfenced instruction at base, and 9+19 only added a hierarchy around it.

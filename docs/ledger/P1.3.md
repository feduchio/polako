## Revision 2: the blocker is gone, and it was never an anomaly

Revision 1 was frozen at `b07f049`, a WIP landed on `task/P1.3-wip` (`98d07b2`), and the item was
blocked on what the handover called *"an unexplained budget resolution"*: a corrupt facade apparently
yielding `{budget: "run_usd", limit: 1}` while the daemon-wide budget resolved to 100.

**There is no anomaly.** The test
`keeps the sound half of a run's persisted budget when the other half is corrupt` writes `facade.json`
**twice**. Its second write is `{ ...metadata, budgetTokens: "lots" }` applied to the *original*
metadata object — so `budgetUsd: 1` is restored and is the **sound** half that the assertion is
about. `limit: 1` is exactly right. The previous session read the first write while reasoning about
the second scenario.

What actually breaks is what the handover said about the other three cases, and it applies to all
four: **they restart repeatedly on one run and rely on spend resetting to zero.** That is the defect
this item removes, encoded as expected behaviour. Verified at `bec1018`: applying the WIP's
seven-line production change fails exactly those four and nothing else, 923 of 927 passing.

Recorded at length because a blocked item and a misread test look identical from the outside, and the
next reader should not re-derive it. `docs/PLAN.md` P1.3 is corrected to match.

## The defect

`ModelBroker.restore(runId)` (`src/broker/broker.ts:277-283`) folds a run's `model.call` events back
into the budget tracker and replays global observations into the catalog. **It has no production
caller** — every call site is a test. `DaemonService`'s recovery is `this.engine.recover()` alone
(`src/daemon/service.ts:110`), which restores scheduler jobs and budget-evaluation boundaries
(`src/engine/engine.ts:143-146`) and nothing about spend.

Consequence: a restarted daemon believes every run has spent nothing, so a run may spend its whole
budget again after each restart. The hard caps accepted in B-selfhost-8 make a run's budget *limits*
survive a restart; without this the limits bind against a counter reset to zero.

## Correction to the plan's own wording

`docs/PLAN.md` P1.3 says: *"`store.repos.runs.listActive()` is **not** the right predicate: it excludes
`NEEDS_HUMAN` phases and `STOPPED` controls, both of which can resume later… Resumable = any run whose
phase is not `DONE` or `FAILED`, regardless of control state."* That sentence came from a reviewer's
claim about a different tree and **is false here.** Verified at `b07f049`:

- `NEEDS_HUMAN` is in `RUN_PHASE_TABLE.terminal` (`src/domain/run.ts:33`), and `answer()` only appends
  to `answers.jsonl` and returns the run still in `NEEDS_HUMAN` (`src/daemon/service.ts:353-360`). It
  does not resume. Making it resume is P1.12 / finding 13, a different item.
- `STOPPED` and `KILLED` are both in the control table's terminal set (`src/domain/run.ts:111`).
  `PAUSED` resumes; `STOPPED` does not.

So the set of runs whose budget can still be consumed is exactly `listActive()` —
`phase NOT IN (DONE, NEEDS_HUMAN, FAILED) AND control NOT IN (STOPPED, KILLED)`
(`src/store/repositories.ts:51-53`).

This is the P1.2 lesson applied in the other direction: a claim justified by machinery has to be checked
against this tree's wiring, and that includes a reviewer's claim.

## Mandatory clauses

**MC1 — restore uses the driver's own predicate, not a hand-written list.** `engine.tick()` drives
exactly `this.store.repos.runs.listActive()` (`src/engine/engine.ts:163`). Restore MUST iterate the same
call. Rationale, and the reason this is a clause rather than an implementation detail: a hand-written
phase list can drift from the set that actually ticks, and then a run would be driven with an unrestored
budget. Sharing the predicate makes that divergence **inexpressible**. When P1.12 widens the resumable
set, both widen together.

**MC2 — restore happens in the constructor, before any tick.** `broker.restore(run.id)` is called for
each run in `listActive()` from the `DaemonService` constructor, on the recovery path. The property
that matters is that **no tick can observe an unrestored budget**, and it holds by construction: the
constructor completes before `start()` installs the timer.

**Its position relative to `engine.recover()` is not load-bearing, and revision 2 stops claiming it
is.** Revision 1 said "immediately following `this.engine.recover()`". Swapping the two passes every
check, and it should: `recover()` rebuilds scheduler jobs and budget-evaluation boundaries
(`src/engine/engine.ts:143-146`) and touches nothing the fold reads, while the fold reads `model.call`
events and touches nothing `recover()` writes. They are independent. The code keeps the stated order
because a reader expects recovery steps together; **no clause claims it and no check observes it**,
per the addendum recorded with P1.10 — an unobservable clause is deleted, not chased.

**MC3 — the restored snapshot equals a fold of the run's own `model.call` events.** No approximation,
no per-task omission. `foldModelCallUsage` is the existing fold and `restore` already uses it.

**MC4 — restoring twice is idempotent.** `restore` replays global observations into the catalog
(`observations.restoreCatalog`), so iterating N active runs replays them N times. That is acceptable
only if it is idempotent; the clause exists because "it is idempotent" was an assumption until this
contract required it to be checked.

**MC5 — a restored budget actually binds.** After restore, a call that would exceed the run's cap is
rejected. Restoring a number that nothing enforces would satisfy MC3 and fix nothing.

**MC6 — no other behaviour changes.** No change to the caps themselves, to `resolveRunSettings`, to
the scheduler, to catalog discovery, or to what `engine.recover()` does.

**MC7 — finding 50, which rides with this item (revision 2).** `BudgetTracker.record` accumulates
per-task tokens into an object literal — `s.perTask[taskId] = (s.perTask[taskId] ?? 0) + tokens`
(`src/broker/quota.ts:163`) — so a `taskId` of `__proto__` sets the prototype instead of creating an
own key and records nothing, after which `assertWithin` reads the prototype object and
`object >= maxTaskTokens` is `false`: **the task spends without limit**. P1.9 fixed the same hazard in
`foldModelCallUsage` and recorded this one as belonging here, because this item is what restores a
persisted snapshot *into* that tracker — `restore` does `perTask: { ...snapshot.perTask }`, which is
the same spread.

The fix is the shape P1.9 used: accumulate in a `Map`, convert once. It is in scope here rather than
deferred again because MC3 requires the restored snapshot to equal the fold **field by field
including `perTask`**, and a tracker that cannot hold the keys the fold can hold makes that clause
unsatisfiable for those keys.

**Severity is stated honestly: latent, not live.** `id("task")` mints against `IdSchema`
(`/^[a-z]+_[0-9a-hjkmnp-tv-z]{22}$/`) and every production path into the tracker passes a `task.id` or
omits the id, so no reachable input produces `__proto__` today. It is fixed because it is one line at
a seam already being opened, not because it is exploitable.

## Acceptance criteria

**AC1** A run with recorded `model.call` usage, after a fresh `DaemonService` is constructed over the
same store, reports non-zero spend for that run.

**AC2** After that restore, a call that would exceed the run's cap is **rejected** (MC5). This is the
criterion that distinguishes a restored number from a restored *constraint*.

**AC3** A run in a terminal phase (`DONE`) is **not** restored — it cannot tick, and restoring it would
be work with no consumer. Asserted so that a future widening is a deliberate act.

**AC4** The restored snapshot equals `foldModelCallUsage` over that run's `model.call` events, compared
field by field including `perTask` and `unknownCostCalls`, not just the token total.

**AC5** Restoring the same run twice leaves the **budget snapshot** unchanged — `restore` replaces
rather than accumulates, which a mutant that `+=`s instead of assigning fails.

**The catalog half of MC4 is observed elsewhere, and revision 3 says so rather than overclaiming.**
Revision 2's AC5 said "leaves the catalog quality state unchanged", which is not what the check reads.
The round-1 Grok lane caught the mismatch and also established the underlying fact: `restoreCatalog`
is **reset-then-replay** — `resetCallStats()`, then `resetQuality` per observed model, then replay
(`src/broker/observations.ts:186-213`) — so replaying it once per active run cannot EMA-accumulate.
Deleting the `resetQuality` step does skew quality, and that mutant is killed by the **pre-existing**
`src/broker/audition.test.ts` EMA-stability check. MC4 therefore holds and is observed; it is simply
not this item's suite that observes the catalog half, and no new check is added to duplicate one that
already exists.

**AC6** Restore iterates `listActive()` itself. Asserted behaviourally: a run excluded from
`listActive()` only by its **control** state (`STOPPED`) is not restored, which a phase-only predicate
would get wrong.

**AC7 — the four adapted cases still observe what they were written for (revision 2).** Each of
`still enforces each run's own override after a daemon restart`,
`falls back to the daemon-wide limit when a run's persisted budget is corrupt`,
`falls back to the daemon-wide USD limit when a run's persisted USD budget is corrupt` and
`keeps the sound half of a run's persisted budget when the other half is corrupt` keeps its original
subject. They are **adapted, not retired**: each gets a fresh run per restart instead of reusing one,
because reusing one only worked while spend reset to zero. The commit message states, per case, what
changed and what did not.

This is the criterion that stops the easy wrong fix. Deleting any of these four, or weakening an
assertion to accommodate restored spend, would make AC1–AC6 pass while removing the coverage that
made the defect visible.

**AC8 — finding 50 (MC7).** `BudgetTracker.record(runId, usage, "__proto__")` records the tokens as an
**own** property, and a subsequent `assertWithin(runId, "__proto__")` **throws** once the per-task cap
is exceeded. At base it records nothing and never throws. Asserted with `Object.hasOwn` or by
comparing `Object.entries`, not by a key lookup, for the reason P1.9 recorded: reading `.constructor`
off a plain object returns something truthy whether or not the key was ever set.

**AC9 — MC3 over hostile keys, through the whole path.** A run whose `model.call` events carry
`taskId: "__proto__"` is created through the daemon, restarted, and its restored `perTask` still has
`__proto__` as an **own** key with the right token count.

**Revision 3 widened this from one hop to the path**, because revision 2's version injected a snapshot
straight into `BudgetTracker.restore` and observed only that hop. The key crosses four copies — the
fold's `Object.fromEntries`, `budgetSnapshotFromUsage`'s spread, `restore`'s spread, and `record`'s
`Object.fromEntries` — and `Object.assign`, the natural alternative at any one of them, drops it
silently. The round-1 reviewer replaced the spread in `budgetSnapshotFromUsage` and all 936 checks
passed. A per-hop criterion does not observe a property of a path.

**AC10 — mutation.** Each must fail a **named** check: removing the restore loop; restoring only runs
whose phase is not terminal, ignoring control state; restoring **all** runs including `DONE`;
reverting `BudgetTracker`'s accumulator to an object literal. Results recorded in the run ledger.

Revision 1 also listed *"calling `restore` before `engine.recover()`"*. **Withdrawn**: it survives
every check because the two steps are independent, which MC2 now states rather than asserting an
order no behaviour depends on.

**MC11 — one new read accessor, and what it returns cannot be written through.**
`ModelBroker.budgetSnapshot(runId)` is added as the read companion to the already-public
`restore(runId)`, because AC4 compares the restored snapshot to the fold field by field and there is
otherwise no way to see the tracker from outside. Recorded as a deliberate addition rather than left
for a reviewer to find, since MC6 forbids other changes.

**Revision 3 strengthens this clause, because revision 2's version was satisfiable and wrong.** It
said the accessor "delegates to `BudgetTracker.snapshot` and mutates nothing", which is literally true
and useless: `snapshot` returned `this.runs.get(runId)`, the **live** enforcement object. Both lanes
found it — one as class (a) with a reproduction that zeroed a run's spend and bypassed the cap, one as
a footgun note. `BudgetTracker.snapshot` now returns a copy, fixing it at the source rather than at
the new accessor, so every caller benefits and no second aliasing path is left behind. The aliasing
was pre-existing; publishing it on the broker is what made it reachable.

**AC11 — nothing the tracker hands out can be written through.** Mutating the object returned by
`budgetSnapshot(runId)` does not change what `assertWithin` enforces, and **every mutable field is
exercised** — `runTokens`, `runUsd`, `perTask` and `unknownCostCalls` — not a sample of them.

**Revision 4 widened this twice, both from round-2 findings.** The copy is shallow *per field*, so
each field is its own opportunity to hand back the stored reference: dropping the copy on
`unknownCostCalls` alone survived all 938 checks while leaving MC11 false. And `BudgetTracker.record`
returned the object it had just stored, so the same write-through existed on a **second** public
surface; it now returns `this.snapshot(runId)`. Fixing one and leaving the other is exactly the
"second aliasing path left behind" that revision 3 gave as the reason for fixing `snapshot` at the
source rather than at the accessor.

The set is finite and therefore enumerable: `BudgetSnapshot` has two mutable children and two
numbers. That is why enumerating them is the right shape here and a sample is not.

**Status:** FROZEN CONTRACT — not implemented, not accepted
**Class:** PHASE_REQUIRED with MISSION_CRITICAL invariants
**Exact base:** `1dc1c5cfbb2f92efb2fa8f58f15e92f02a3c80b2` (accepted B-selfhost-7)
**Source finding:** `docs/ledger/B-selfhost-remaining.md` item **8**

Not item 12 (crash recovery of run state). Not C2 (adaptive/pathology budget policy). Not items 9, 11, 13–17, 21, 22. After freeze, do not rewrite.

## Authority

1. Finding 8: `--budget-tokens` / `--budget-usd` are validated and stored in facade metadata; `applyRunBudgetOverrides` is unused; Option A hard caps required, not C2.
2. Exact base behavior as in `src/broker/quota.ts`, `src/broker/broker.ts`, `src/daemon/composition.ts`, `src/daemon/service.ts` and `src/convergence/pathology/**`.
3. B-selfhost-7 accepted: `PhaseContext.config` resolves per run through `EngineOptions.resolveRunConfig`, and its MC1 forbids assigning into the shared `PolishConfig`. That prohibition remains in force.

## Defect

A run's budget override reaches storage and stops there.

`DaemonService.createRun` validates `budgetTokens` / `budgetUsd` (`src/daemon/service.ts:177-182`) and writes them into the run's `facade.json` (`:229-230`). Nothing reads them back for enforcement. `applyRunBudgetOverrides` (`src/daemon/composition.ts:113-122`) is re-exported from `src/daemon/index.ts:4` and has no caller anywhere — not in production, not in tests.

Enforcement is a single shared object. `BudgetTracker` is constructed once per daemon (`src/daemon/composition.ts:142`, the only production construction) and holds one `limits` field (`src/broker/quota.ts:99`). It already partitions *spend* by run (`private readonly runs = new Map<string, BudgetSnapshot>()`, `:97`), so the asymmetry is only in the limits. The pre-call guard reads that one field for every run (`src/broker/quota.ts:115-126`), called from `src/broker/broker.ts:69` before every model call. This is the Option A hard cap the finding requires; exceeding it throws `CONFLICT` carrying a `budget` detail, which `AgentRunner` maps to `BUDGET_EXCEEDED` (`src/agents/runner.ts:83-85`).

A second surface reads limits through configuration rather than through the tracker: `createConvergenceDriver` → `buildPathologySample` (`src/convergence/pathology/sample.ts:334-365`, called at `src/engine/convergenceDrivers.ts:97-102`) → `buildPathologyBudgetSnapshot` (`sample.ts:357-363`) → `liveBudgetLimits` (`src/convergence/pathology/budget.ts:101-108`). An exhausted dimension drives `BUDGET_STOP` → phase `FAILED` with terminal reason `budget_exhausted` (`src/engine/convergenceDrivers.ts:119-129`, `:209-218`, `:285-305`). `buildPathologySample` takes `config: Pick<PolishConfig, "budget" | "review">` (`sample.ts:337`); in production that argument is `ctx.config`, which B-selfhost-7 already made per-run.

The same defect exists a second time, one layer down. `ConvergenceDriverOptions.cliBudget` (`src/engine/convergenceDrivers.ts:46`) is threaded through `sample.ts:338,362` to `budget.ts:141,150` and is supplied by nobody — the only production construction site omits it (`src/daemon/composition.ts:337-342`), and no test supplies it either. Consequently `unusedCliMetadata` (`src/convergence/pathology/budget.ts:110-119`) returns `{ budgetTokens: null, budgetUsd: null, applied: false }` on every path. The field is presently honest. Any fix that leaves `applied` hardcoded makes it a lie.

## Definitions and boundaries

**Overridable limits.** Only `budget.maxRunTokens` and `budget.maxRunUsd`. `maxTaskTokens` and `maxRunWallClockMinutes` have no CLI or RPC flag and must continue to come from the loaded configuration for every run.

**Override replaces, it does not clamp.** For the run that carries it, an override replaces the configured value in both directions: it may lower a finite configured cap and it may raise one. It is not `Math.min`-ed against the configured value. This matches `applyRunBudgetOverrides` (`src/daemon/composition.ts:118-119`).

**The tracker's limits alias the config.** `new BudgetTracker(options.config.budget)` (`src/daemon/composition.ts:142`) passes the loaded config's `budget` object **by reference**, so at base `tracker`'s limits and `config.budget` are the same object. "Do not mutate the shared config" and "do not mutate the tracker's default limits" are therefore one prohibition, and one static pin covers both. The field is declared `private readonly limits: BudgetLimits` (`src/broker/quota.ts:99`); reassigning it requires deleting `readonly`, which is forbidden by MC2.

**A USD cap only binds on priced calls.** `BudgetTracker.record` accumulates `runUsd` only when `usage.costUsd` is non-null; unpriced calls accumulate in `unknownCostCalls` instead (`src/broker/quota.ts:137-143`). `ScriptedProvider` defaults to `costUsd: null` (`src/providers/scripted.ts:60`), so a USD acceptance check must script a step with an explicit `costUsd`. C2's surface has the same asymmetry — it compares against `knownRunUsd` (`src/convergence/pathology/budget.ts:124`). This is base behavior and is not changed here.

**The reachable observation seam.** `BudgetTracker` is not reachable from a `DaemonService`: `ProductionDeps` exposes no budget field (`src/daemon/composition.ts:91-101`) and `ModelBroker` holds it behind `private readonly deps` (`src/broker/broker.ts:59`) with no accessor. Enforcement must therefore be observed through `service.productionComposition().broker.complete({...})`, which is the production call into `assertWithin`. Identify the throw with `isBudgetError` (`src/broker/quota.ts:150-152`) plus `details.budget` and `details.limit` (`:118`, `:121`). Do **not** add an accessor merely to make a test easier, and do **not** use `DaemonServiceOptions.productionDeps` (`src/daemon/service.ts:48`) to inject a pre-built tracker: that bypasses `loadPolishConfig` (`:71`) and silently diverges `this.config` from `deps.config`, which would make the "loaded configuration" checks meaningless.

**Item-12 boundary.** Reading the `budgetTokens` / `budgetUsd` fields already written to a run's `facade.json` is permitted, exactly as B-selfhost-7 reads `runtime` from the same file. Restoring accumulated *spend* is not permitted here: `ModelBroker.restore(runId)` (`src/broker/broker.ts:274-280`) has no production caller at base — every call site is a test — so a restarted daemon already forgets what a run has spent. That gap belongs to item 12. A conforming implementation makes a run's *limits* survive a restart and must not claim the cap itself is restart-durable.

**Not C2.** No adaptive budget, no change to `BUDGET_STOP` policy, decision shapes, or when observation boundaries occur. Permitted changes under `src/convergence/pathology/**` are only those required by MC7 and MC8.

## MISSION_CRITICAL invariants

1. **The override is enforced.** A run created with `budgetTokens` has that value as the run-token limit actually applied by `BudgetTracker.assertWithin` for that run, and likewise `budgetUsd` for the run-USD limit on priced calls. Demonstrated by a throw for the overridden run under a loaded configuration that would have allowed the call.
2. **Isolation is structural, not temporal.** A run's override must not change the limits enforced for any other run, whether created before or after, and whether or not it is in flight. Specifically: the shared `PolishConfig` must not be assigned into; `BudgetTracker`'s constructor limits field must remain `private readonly` and must never be the target of an assignment; per-run limits must live in a separate run-keyed structure consulted by `assertWithin`, with the constructor limits as the fallback. Resolve-and-assign-before-assert is forbidden even though it is synchronous and therefore invisible to any concurrency test.
3. **Runs without overrides are unchanged.** A run created with neither flag enforces exactly the loaded configuration's `maxRunTokens` and `maxRunUsd`, as at base.
4. **`null` semantics preserved.** A configured limit of `null` means unlimited. An override replaces `null` with a finite cap for that run only; the absence of an override never turns a finite configured limit into `null`, nor `null` into a finite one. A partial override leaves the other dimension at its configured value.
5. **Only the two documented limits are overridable.** For every run, `maxTaskTokens` and `maxRunWallClockMinutes` equal the loaded configuration's values. Both wall-clock sites keep using the shared config: `enqueueBudgetDeadlineJob` (`src/engine/engine.ts:102`) and `appendDueBudgetEvaluationBoundaries` (`:144`, `src/convergence/pathology/deadline.ts:62-78`).
6. **Validation preserved.** `budgetTokens` must remain a positive integer and `budgetUsd` a positive number, rejected before any run row or branch is created (`src/daemon/service.ts:177-182`). The CLI keeps `positiveInteger` for `--budget-tokens` (`src/cli/index.ts:36`, `:189-192`) and its bare `Number()` for `--budget-usd` (`:37`), whose effective validation is daemon-side.
7. **One truth for both surfaces.** For any run, `maxRunTokens` and `maxRunUsd` as enforced by `assertWithin` equal the same two fields of `liveBudgetLimits` for that run, and both derive from a single resolution of that run's overrides. `maxTaskTokens` equals the loaded value on both surfaces. `maxRunWallClockMinutes` is outside this invariant: the broker guard has no wall-clock dimension (`src/broker/quota.ts:11-15`).
8. **No field may misreport, and none may be removed.** For a run with an applied override, `PathologyBudgetSnapshot.unusedCliMetadata` reports that run's override values with `applied: true`; for a run without one it reports `{ budgetTokens: null, budgetUsd: null, applied: false }`. Removal or renaming is **not** permitted: the snapshot is persisted verbatim inside `pathology.sample` payloads (`src/convergence/pathology/persist.ts:55-62`) and read back with an unchecked cast (`:13-19`) at an unchanged `PATHOLOGY_SAMPLE_VERSION` of 1 (`src/convergence/pathology/types.ts:8`), so a shape change would fork the schema silently. `applied` is a literal `false` type (`types.ts:52-56`); widening it is expected.
9. **Post-restart resolution and enforcement.** After a daemon restart, each run enforces its *own* persisted overrides, or, if its metadata is missing or unreadable, the loaded configuration's limits. It must never enforce another run's overrides, and the result must not depend on the order in which runs are first touched after the restart. Resolution must be lazy from persisted metadata, because `engine.recover()` runs in the constructor (`src/daemon/service.ts:95`) and a recovered run never passes through `createRun`. Accumulated spend is out of scope per the item-12 boundary.
10. **Registration precedes visibility.** A run's limits must be registered before the run can be driven or can issue a model call. `engine.createRun` (`src/daemon/service.ts:192`) makes a run tickable and the first `await` follows at `:214`, with `writeMetadata` only at `:232`, so registration must not sit behind an `await`.
11. **No accepted-and-ignored input survives.** Both dead paths must be closed: `applyRunBudgetOverrides` and the `cliBudget` parameter chain (`src/engine/convergenceDrivers.ts:46`, `src/convergence/pathology/sample.ts:338`, `src/convergence/pathology/budget.ts:141`). Each must either become a production path or be deleted. Wiring the override through `ctx.config` while leaving `cliBudget` unsupplied restates this very finding one layer down and does not satisfy this contract.
12. **No scope creep.** No items 9/11–17/21/22, no C-tasks, no C2 policy change, no item-12 spend recovery, no FSM widening, no Composer, no live-paid providers.

## Acceptance checks

1. **Token override binds:** a run created through `handle("run", …)` with `budgetTokens: N` throws a budget `CONFLICT` (`details.budget === "run_tokens"`, `details.limit === N`) from a `broker.complete` call once that run has recorded ≥ N tokens, under a loaded configuration whose `maxRunTokens` is `null` or larger. It must not throw below N.
2. **USD override binds:** the same for `budgetUsd` with a non-integer value, using scripted steps that carry an explicit `costUsd` (see *A USD cap only binds on priced calls*).
3. **Both flags together:** a run supplying `budgetTokens` and `budgetUsd` enforces both, each at its own threshold.
4. **No leak to an earlier run:** create A without overrides, then B with a small override; A still enforces the configured limits and does not throw at B's threshold.
5. **No leak to a later run:** create A with a small override, then B without; B enforces the configured limits.
6. **Concurrent isolation:** create A and B through `handle("run", …)` with different overrides. Script a provider whose `complete` parks on a promise the test releases, so A's call is suspended *inside* `adapter.complete` (`src/broker/broker.ts:111`), past A's `assertWithin`. While A is parked, issue B's call and assert it is governed by B's limit; create a third run C with another override while A is still parked; then release A and assert A's next call is still governed by A's limit.
7. **Default limits untouched:** after driving overridden runs, the limits the tracker was constructed with still equal `service.getConfig().budget` on the three `BudgetLimits` dimensions, and a run created afterwards with no override still throws at the configured threshold.
8. **Static pin:** no non-test file under `src/**` contains an assignment matching `/\.(budget|limits)(\.\w+)?\s*=(?!=)/`, and `BudgetTracker`'s limits field is still declared `private readonly`. Model this on `src/daemon/service.runtime-mode.test.ts:50-61`.
9. **Unchanged without overrides:** a run created with neither flag throws at the configured threshold and not before.
10. **`null` means unlimited:** with `maxRunTokens: null` configured and no override, a large recorded usage does not throw.
11. **An override may raise a cap:** with `maxRunTokens: 100` configured, a run with `budgetTokens: 1000` does not throw at 150 recorded tokens and does throw at 1000, while a sibling run with no override throws at 100.
12. **Non-overridable limits:** with `maxTaskTokens` configured, a run with a `budgetTokens` override still enforces the configured per-task cap; `maxRunWallClockMinutes` still governs the deadline job.
13. **Validation:** invalid `budgetTokens` (`0`, `-1`, `1.5`) and invalid `budgetUsd` (`0`, `-1`) reject with `CONFIG_ERROR`; afterwards `handle("status", {})` returns `[]`, `getConfig().budget` is unchanged, and a subsequently created run with no override still enforces the configured limits.
14. **Both surfaces agree:** for a run with an override, the limits C2 reports equal the two limits the broker enforces. Assert on the sample the *registered* `CONVERGENCE_CHECK` driver builds when driven through the engine for that run — not on a hand-built `PhaseContext` and not on a hand-built snapshot. A `budget.evaluated` event is unconditionally an observation boundary (`src/convergence/pathology/sample.ts:21-29`, `:86-87`) and is the cheapest way to reach a sample.
15. **No misreporting:** the persisted `pathology.sample` event for a run with an override carries `unusedCliMetadata` equal to that run's override values with `applied: true`, and for a sibling run without one, `{ budgetTokens: null, budgetUsd: null, applied: false }`.
16. **Post-restart:** create A (`budgetTokens: 1`) and B (`budgetTokens: 10_000`); close the service; open a fresh `DaemonService` over the same home; without any new `handle("run", …)`, drive broker calls for A and B. A throws with `details.limit === 1`, B does not throw below `10_000`, and the outcome is the same whichever of A or B is touched first.
17. **Registration precedes visibility:** drive the engine from inside a spy on `Git.createBranch`, before `writeMetadata` runs, and assert the run's override is already in force. Model this on `src/daemon/service.runtime-mode.test.ts:153-175`.
18. **Shared config untouched:** after creating runs with overrides, the loaded `PolishConfig` is unchanged, `getConfig()` still returns the same instance as `productionComposition().config`, and B-selfhost-7's static pin still passes.
19. **Regression:** `src/broker/broker.test.ts`, `src/engine/budget-deadline.test.ts`, `src/convergence/pathology/pathology.test.ts`, `src/engine/convergence-c2.test.ts`, `src/daemon/service.runtime-mode.test.ts` and `src/engine/run-config.test.ts` stay green. ## Anti-fake notes for reviewers

- **Storing is not enforcing.** A test asserting that a limits object was registered, or that `facade.json` contains the numbers, proves nothing. Require a throw at the overridden threshold and no throw just below it.
- **Resolve-and-assign before the assert is the cheapest fake and no concurrency test can catch it.** `assertWithin` is synchronous (`src/broker/quota.ts:115-126`) and runs at the top of `complete` before any `await` (`src/broker/broker.ts:69` versus `:100`). An implementation that assigns the run's limits into the shared field immediately before the assert is correct by accident under single-threaded semantics. AC7 and AC8 are what kill it — verify both are present and that AC8's regex actually fires when you plant such an assignment.
- **Save-set-restore spanning the awaits does leak.** An implementation that sets limits before `adapter.complete` and restores after (for instance around the callback in `createWorkerFactory`, `src/daemon/composition.ts:545-546`) must fail AC6.
- **Mutating the shared `PolishConfig`** is the same fake one level up. B-selfhost-7's pin does *not* catch it: that regex matches only `runtimeValidation` (`src/daemon/service.runtime-mode.test.ts:57`). AC8 is the pin that covers `budget`.
- **Per-run limits resolved in one surface only.** Broker-only leaves C2 reporting shared limits; config-only leaves the tracker unchanged so no cap binds. AC1 kills the second, AC14 the first — and AC14 only has teeth if it drives the registered driver.
- **A per-run map that `assertWithin` never consults** passes any getter-based check. AC1 and AC4 kill it.
- **`applied: true` hardcoded** is the mirror of the defect. It must be true because the override is in force, and false for a run without one — AC15 asserts both halves for that reason.
- **Deleting `applyRunBudgetOverrides` and stopping there** satisfies "no uncalled export" while implementing nothing. AC1 kills it. Deleting the `cliBudget` chain instead of supplying it is permitted by MC11 only if nothing then misreports, which AC15 still requires.
- **A single-run restart check** is passable by a resolver that reads whichever `facade.json` it finds, or caches the last override seen — the precise defect class B-selfhost-7 existed to fix. AC16 uses two runs and asserts order-independence for that reason.
- Daemon-level checks must use the real `handle("run", …)` path and the daemon's own composition. `createBranch` is `git branch` and does not move HEAD, so several runs may share one temporary repository.

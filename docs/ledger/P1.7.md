**Status:** FROZEN, revision 1. **Base:** HOST `0fa4704` on `phase-c-collab` (code identical to the
accepted P1.9 commit `485132b`). **Plan reference:** `docs/PLAN.md` §3 P1.7. **Goal served:** G2.
Closes findings 12 (settings half), 17, 21, 22, 25. **Process:** `docs/BVP.md` Process v2. Touches

## One seam, five findings

`DaemonService.runConfig` (`src/daemon/service.ts:451-461`) derives a run's effective configuration.
Around it sit five recorded defects that are all the same shape: **the run's settings are resolved in
more than one place, and the places disagree.**

| # | Defect | Site |
|---|---|---|
| 12 | run settings and runtime mode are re-derived per process, not owned | `service.ts:451-461`, `:488-496` |
| 17 | `polish.toml`'s `runtimeValidation.mode` is never effective, because an omitted `--runtime` becomes `"auto"` before anything can tell it was omitted | `cli/index.ts:24`, `service.ts:147` |
| 21 | a corrupt `facade.json` silently downgrades a `required` run, with no event | `service.ts:488-496`, `:473-485` |
| 22 | the guard against mutating the shared config is a **source grep** | `service.runtime-mode.test.ts:50-61`, `service.budget-override.test.ts:119-132` |
| 25 | `applyRunBudgetOverrides` is applied at two independent sites | `service.ts:459`, `composition.ts:195-197` |

### Finding 17, stated exactly, because it is easy to get half right

`cli/index.ts:24` is `const runtime = flag(args, "--runtime") ?? "auto"`, and `service.ts:147` is
`runtime: optionalString(params, "runtime") ?? "auto"`. **Both** default. Fixing only the CLI leaves
the RPC defaulting for any other client; fixing only the RPC leaves the CLI sending `"auto"`
explicitly. The information that the user said nothing has to survive both boundaries, which is why
the plan specifies the RPC payload carrying `runtime: null`.

The existing check `resolves an omitted runtime argument to auto rather than the configured mode`
(`service.runtime-mode.test.ts:135-143`) **encodes the defect as expected behaviour**. It is retired
by this item, not adapted.

## A correction to the plan: there are three consumers, not two

`docs/PLAN.md` P1.7 says the resolver is *"owned by `DaemonService` and called by both consumers"* and
names the engine's `resolveRunConfig` and the broker's budget closure. Verified at `0fa4704`, there is
a **third**: `composition.ts:403`, `resolveCliBudget: (ctx) => deps.resolveRunBudget?.(ctx.run.id)`,
which feeds `unusedCliMetadata` into the pathology sample (`src/convergence/pathology/budget.ts`).

It needs something the other two do not. The engine and the broker want the **resolved limits** — what
binds. `unusedCliMetadata` wants the **overrides** — what the user asked for — because its whole job
is to record whether a CLI budget flag was supplied and applied. Those are different values and
neither can be derived from the other: resolved limits that equal the daemon-wide defaults are
indistinguishable from no override at all.

So the resolver's return type carries both, and this is a clause rather than an implementation
detail because an implementer who returns only `BudgetLimits` will make `unusedCliMetadata` report
`applied: false` on every run that overrode a flag to the same value the config already had.

## A decision the plan leaves open: what an unspecified mode resolves to, and when

With finding 17 fixed, a run created with no `--runtime` takes its mode from `polish.toml`. **When?**

- *Resolve on every read* — then editing `polish.toml` changes a running run's mode mid-flight, and a
  run recovered after a restart can differ from the same run before it. That reintroduces finding 12
  in a new place.
- *Resolve once at creation and persist the resolved mode* — the run's mode is a property of the run.

**This contract takes the second.** `createRun` resolves the mode once and writes the **resolved**
value to `facade.json`. A run is not "unspecified" after it exists; it has a mode. Recorded here
because both readings are defensible and the choice is invisible in the diff.

## Mandatory clauses

**MC1 — one resolver, and divergence is unrepresentable.** `DaemonService` gains

```
private resolveRunSettings(runId: string): ResolvedRunSettings
type ResolvedRunSettings = {
  config: PolishConfig;      // the run's effective config, mode and budget merged
  budget: BudgetLimits;      // from src/broker/quota.ts, the resolved limits that bind
  overrides: RunBudgetLimits;// what the user asked for, for unusedCliMetadata only
}
```

All three consumers read it. `applyRunBudgetOverrides` is called from **exactly one** place in
production. `withRuntimeValidationMode` is called from exactly one place in production.

**MC2 — one cache.** The two maps `runtimeModes` and `runBudgets` (`service.ts:73`, `:75`) are
replaced by a single `Map<string, ResolvedRunSettings>`. Two caches keyed on the same id, filled on
different paths, is finding 12's shape at process scope. `createRun`'s pre-registration before its
first `await` is preserved — a tick landing mid-creation must still see the run's own settings, which
`service.runtime-mode.test.ts:153-175` observes.

**MC3 — "not specified" survives both boundaries.** `cli/index.ts` stops defaulting `--runtime`; the
RPC accepts `runtime` as `string | null | absent`; `service.handle` passes `null` through rather than
`"auto"`. Only `resolveRunSettings` — and only at creation — turns `null` into
`config.runtimeValidation.mode`.

**MC4 — an invalid runtime is still rejected, and rejected before the run exists.** `null` means
unspecified; `"sometimes"` is still a `CONFIG_ERROR` thrown before `engine.createRun`.
`service.runtime-mode.test.ts:145-151` stays and must keep passing.

**MC5 — a fallback is an event, not a silence.** `run.settings_fallback` joins `KNOWN_EVENT_TYPES`
(`src/domain/event.ts:10-71`) with payload
`{ reason: string; requestedMode: RuntimeValidationMode | null; effectiveMode: RuntimeValidationMode }`.
`runId` is on the envelope, not in the payload.

- `reason` is one of exactly: `"facade_unreadable"`, `"runtime_invalid"`, `"budget_tokens_invalid"`,
  `"budget_usd_invalid"`. When more than one applies they are joined with `,` in that order, so the
  value is a stable, greppable string rather than an arbitrary sentence.
- `requestedMode` is **`null` when `facade.json` is unreadable**, because the requested value exists
  only in that file. It is the parsed mode when the file was readable but another field was corrupt.
- **Emitted at most once per run**, keyed on `runId` in a `Set`, not once per `resolveRunSettings`
  call. This is the clause the plan calls out by name, and the reason is that the resolver runs on
  every tick and every model call.

**MC6 — the fallback is per dimension, not all-or-nothing.** A facade with a sound `budgetTokens` and
a corrupt `budgetUsd` keeps the tokens. This is existing behaviour
(`service.budget-override.test.ts:601-625`) and MC5 must not regress it: the event records what was
discarded, it does not widen what is discarded.

**MC7 — `withRuntimeValidationMode` copies unconditionally.** The early return
`if (base.runtimeValidation.mode === mode) return base;` (`src/domain/config.ts:297`) is removed.
Returning `base` hands a caller the shared config object whenever the modes happen to match, which is
precisely the case a test using the default mode exercises and production does not.

**MC8 — both source-grep pins are retired, not widened.** `never assigns runtimeValidation anywhere in
non-test source` and `never assigns a budget or limits field in non-test source` (including its
`expect(quota).toContain("private readonly limits: BudgetLimits")`) are deleted.

The argument is the one this phase has now reached twice. A grep over source quantifies over code that
could be written, and the round-3 reviewer of P1.10 and both reviewers of P1.9 showed the same thing
each time: `config["runtimeValidation"].mode = x` and `Object.assign(config.runtimeValidation, …)` both
evade this regex, so it does not establish what it claims. `docs/ledger/PHASE-C.md`'s stopping-rule
addendum says the answer is to delete the clause, not to widen the pattern.

**What replaces them is stronger, and this is the part that must not be lost.** The property the pins
were reaching for — *a run's settings never leak into another run or into the shared config* — is
observed **behaviourally** by checks that already exist and that MC9 requires be kept:
`leaves the loaded config object untouched when runs request other modes`,
`isolates concurrent runs across an await boundary inside one engine tick`,
`does not change an active run's mode when a later run is created`,
`does not leak an override onto a run created earlier` / `…later`,
`keeps each run on its own limit while another run's call is in flight`, and
`leaves the loaded config instance shared and untouched`. MC7's unconditional copy is what makes
those true by construction rather than by discipline.

**MC9 — every retired check is named, and no behavioural check is retired.** The commit message lists
each deleted case from `service.runtime-mode.test.ts` and `service.budget-override.test.ts` with the
reason. A case may be retired only if it (a) encodes a defect this item fixes — finding 17's — or
(b) is a source grep under MC8. **Any case that drives the daemon and asserts an observable stays.**
If a behavioural case needs its expectation changed, that is an adaptation and the commit message says
what changed and why.

**MC10 — no behaviour changes beyond the five findings.** Per-run isolation, the caps themselves, the
scheduler, catalog discovery, and `engine.recover()` are untouched. Spend restoration across restart
is **P1.3** and is not in this item.

## Acceptance criteria

**AC1 — the plan's verify (a): one resolver.** Exactly one production call site each of
`applyRunBudgetOverrides` and `withRuntimeValidationMode`, and all three consumers reach
`resolveRunSettings`. Asserted behaviourally: for a run with both a budget override and a non-default
mode, the limits the broker enforces, the limits C2 reports, and the mode at the `PhaseContext`
boundary are all consistent with one resolution. `service.budget-override.test.ts:336-374` already
drives the first two; this extends it to the mode.

**AC2 — the plan's verify (b): `polish.toml` becomes effective.** A run created with **no**
`--runtime`, with `polish.toml` at `required`, resolves `required` at the `PhaseContext` boundary. At
base it resolves `auto`. This is the single criterion that discriminates finding 17 fixed from finding
17 present.

**AC3 — the CLI half of AC2.** The same, driven through `cli/index.ts`'s argument parsing rather than
through `service.handle` directly: with no `--runtime` the params sent carry no mode, not `"auto"`.
Asserted separately because MC3's point is that **two** boundaries defaulted and fixing one is
invisible to a check of the other.

**AC4 — an explicit flag still wins.** `--runtime off` with `polish.toml` at `required` resolves
`off`. Guards against a fix that reads the config unconditionally.

**AC5 — the plan's verify (c): one event, not two.** Two `resolveRunSettings` calls on a run with a
corrupt `facade.json` produce exactly **one** `run.settings_fallback`. Driven by ticking the run more
than once, not by calling the private method twice.

**AC6 — the event says what happened.** For an unreadable `facade.json`: `reason` is
`"facade_unreadable"` and `requestedMode` is `null`. For a readable facade with `runtime: "sometimes"`:
`reason` is `"runtime_invalid"` and `requestedMode` is `null` — the file was readable but the mode in
it was not a mode. For a readable facade with a sound mode and `budgetUsd: "lots"`: `reason` is
`"budget_usd_invalid"`, `requestedMode` is the sound mode, and `effectiveMode` equals it.

**AC7 — no event when nothing fell back.** A run with a sound facade produces **no**
`run.settings_fallback` over any number of ticks. A fix that emits unconditionally would satisfy AC5
and AC6.

**AC8 — MC6, the sound half survives and is reported.** A facade with `budgetTokens: 30` and
`budgetUsd: "lots"` still binds 30 tokens **and** emits one event with
`reason: "budget_usd_invalid"`. The existing case asserts the first half only.

**AC9 — MC7, the copy is unconditional.** `withRuntimeValidationMode(base, base.runtimeValidation.mode)`
returns an object that is **not** `base` (`toBe` fails, `toEqual` passes) and whose
`runtimeValidation` is not the same object either. At base the first assertion fails.

**AC10 — MC8's replacement is real.** The named behavioural isolation checks listed in MC8 all pass,
and each is confirmed to fail under a mutant that mutates the shared config in place. If a mutant that
writes `this.config.runtimeValidation.mode = mode` passes every one of them, MC8 has removed a check
and replaced it with nothing, and this AC fails.

**AC11 — `unusedCliMetadata` still distinguishes asked-for from defaulted.** A run whose
`--budget-tokens` equals the configured `maxRunTokens` reports `applied: true`, and a run with no flag
reports `applied: false`, with the same configured value in both. This is the criterion that
discriminates a resolver returning `overrides` from one returning only `BudgetLimits`.

**AC12 — the mode is frozen at creation.** A run created with no `--runtime` under `polish.toml` at
`required`, then restarted after `polish.toml` is changed to `off`, still resolves `required`. This
observes the decision recorded above, which is otherwise invisible.

**AC13 — mutation.** Each must fail a **named** check: restoring either boundary's `?? "auto"`;
restoring the early return in `withRuntimeValidationMode`; emitting the fallback event per call
instead of per run; emitting it unconditionally; returning only `BudgetLimits` from the resolver;
discarding both budget halves when one is corrupt; resolving the mode from config on every read
instead of at creation. Results recorded in the run ledger.

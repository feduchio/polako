# R2 — A clean round has to be earned

**Plan:** `docs/RECOVERY.md` §3 R2. **Base:** `fe686f0`.
**Reviewer lane:** GPT (`gpt-5.6-sol-high`), one lane.

**Process note.** `docs/BVP.md` level 1 §1 says the contract is frozen before the code. For this
item the required behaviour was already written in `docs/RECOVERY.md` §3 R2 and this file refines
it, but the refinement was written after the implementation. Recorded rather than hidden.

## Defect (normative)

`docs/RECOVERY.md` §1.1: across twelve days and twenty runs the `findings` table holds **0** rows,
`finding_validations` 0, and all six recorded `clean_rounds` have `rawFindings: 0`
(`sqlite3 "file:$HOME/.polish/polish.db?mode=ro" "select count(*) from findings;"`). Both `DONE`
verdicts were reached exactly the way the founding document forbids in as many words: the model
said it was fine.

Nothing in the product could have told anyone. A round of reviews that returns nothing is recorded
as a clean round, and three clean rounds are `DONE`. The verdict "no findings" is treated as
evidence about the code, when it is equally consistent with a reviewer that cannot produce a
finding at all — which is what §1.2 shows was in fact the case.

## Required end state

1. Before a clean round is recorded, every model that **produced** that round is put through a
   seeded-defect canary: a diff carrying one planted, ordinary defect, sent down the identical call
   path a real review takes — same prompt composition, same response schema, same parsing, same
   shape normalisation. A shorter path would verify the wrong thing: §1.2's whole point is a
   normalisation that shipped on 12 September and has never executed in production.
2. A model that reports nothing on that diff is not verified, and neither is one that could not be
   asked. Silence is not an answer.
3. An unverified round does not become a clean round and the run reaches
   `NEEDS_HUMAN("review unverifiable")` — a distinct terminal code, so the condition is countable
   afterwards and cannot be confused with a provider outage.
4. Once per model per run. The question is whether this reviewer on this transport can report
   anything, and that does not change between rounds.

## Acceptance checks

1. The plan's own check: a run whose reviewer returns an empty result on the seeded defect does not
   reach `DONE`. Stronger here — it does not reach a clean round.
2. A reviewer that reports the seeded defect leaves the clean round recorded and the run
   proceeding, with the canary verdict in the event log.
3. A canary call that fails at the provider is unverified, and the recorded verdict says why.
4. One provider call per model per run, across two rounds.
5. No canary call at all when no clean round is pending — the cost is paid only where a verdict
   would otherwise be granted.
6. Gate green at Node 24.

## Non-goals

- The negative half of a canary pair: clean code must produce **no** finding. That measures
  fabrication, which is a different failure from the one observed, and `docs/PLAN.md` item 42
  already measures it offline. A successor if a run shows invented findings.
- Choosing better reviewers, or how many. R1c and R5.
- Making the canary defect configurable. One planted defect that everything sees is what makes the
  verdicts comparable between runs.

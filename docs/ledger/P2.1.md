# P2.1 — Post-validation yield

**Status:** FROZEN, revision 1. **Base:** HOST `f9195d1`.
**Plan reference:** `docs/PLAN.md` §4 P2.1. **Goal:** G1 (measurement only).
**Gates:** P3.1. **Process:** v3.

This item measures. It changes no production behaviour, and the numbers are not
known when this contract is frozen — which is the point of freezing the method
first.

## What is being measured, and what is not

The 60.0% clean-site false-positive figure was taken on **raw reviewer output**.
Production passes findings through triage and reproduction
(`src/findings/validator.ts:82-161`, `src/engine/checkpointCheckout.ts:88-104`,
`src/engine/reviewDrivers.ts:206-249`). What survives that has never been
counted.

A count of survivors is **attrition, not precision**. It cannot say which
survivors are false positives; only hand-adjudication of the survivors can, and
that is admissible only over the eligible set defined in MC1.

## Mandatory clauses

**MC1 — the eligibility cut-off is a commit, not a judgement.** A review
execution is **eligible** only if the `review.finished` event that recorded it
has `ts` at or after the author timestamp of `3f23ede` — finding 41's parser
fix, `2026-09-12T18:43:57Z`, `1789238637000` ms — because before that commit the
request asked for a JSON object while `parseRawFindings` demanded an array, so
an earlier execution's recorded emptiness is **discarded parser output** and not
yield. The report states the cut-off as both the commit and the epoch value it
used.

Two consequences, both recorded rather than left to the reader. The cut-off is
wall-clock against a code change, so it is an **upper bound** on eligibility: a
daemon could have been running an older build after that instant, never a newer
one. And eligibility is decided **per execution**, not per run, because a run
that began before the fix and reviewed after it parsed those later responses
correctly.

**MC2 — the eligible report is per axis, and the join is stated.** For the
eligible set the report gives, per axis: raw findings, findings surviving
triage, findings surviving reproduction, tasks spawned, and reviewer tokens.
`ReviewExecution` (`src/domain/review.ts:21-33`) carries no token fields, so
tokens come from `events` of `type = 'model.call'` with `payload.role ==
'reviewer'`, attributed by `payload.purpose == "review_<axis>"`. A call whose
`payload.usage` is `null` contributes 0 tokens and is counted separately, the
same rule `docs/PLAN.md` §1 fixes for the cost gate.

**MC3 — the verdict when the eligible set is empty.** P2.1 reports exactly
**`inconclusive — no post-plumbing production findings`**, and states the
eligible execution count and the cut-off applied. It does **not** report a yield
of zero, a false-positive rate, or any per-axis ranking. There is nothing to
hand-adjudicate when no survivor is eligible, and the report says so instead of
adjudicating ineligible rows.

**MC4 — the ineligible population is reported separately and labelled.**
Pre-cut-off executions are counted and described as discarded parser output.
Their findings, validations and tokens never enter the eligible per-axis table,
and no aggregate mixes the two populations.

**MC5 — the instrument reproduces figures recorded before it existed.** Over
the whole store, without the cut-off, the instrument must reproduce the
independently recorded values in `docs/ledger/g1-baseline.md` and finding 41:
`model.call` events with `role == 'reviewer'` = **209**, of which
`usage: null` = **83**; attributed reviewer tokens = **834,635**; completed
review executions = **18**. Any mismatch is reported as a mismatch, with both
values, and is not adjusted away. This is what stands in for a unit test of an
instrument whose only output is a report.

**MC6 — read-only, and outside production.** The store is opened with
`readOnly: true` and never through `openDb` (`src/store/db.ts:24-33`), which
runs migrations and would write to the file. The instrument lives under
`scripts/`, so `pnpm deps:check` over `src` and the daemon composition are
untouched. `git diff f9195d1..HEAD -- src/` is empty for this item.

**MC7 — no scope beyond P2.1.** No production change, no config field, no new
event type, no change to review dispatch, and no growth of the P2.2 replay set.

## Acceptance criteria

1. The report names the cut-off commit and epoch value, and the eligible count.
2. The eligible per-axis table exists, or the MC3 verdict is recorded with its
   eligible count — never both.
3. The ineligible population is counted separately and labelled as discarded
   parser output.
4. All four MC5 reproduction values are stated with their measured counterparts.
5. The consequence for P3.1 is recorded: if the verdict is `inconclusive`, P3.1
   reports `inconclusive — no post-validation yield data` and drops no axis,
   and P3.2/P3.3 are not thereby void (`docs/PLAN.md` §5 P3.1).
6. The instrument is committed, takes a store path, and reruns to the same
   numbers on the same store.

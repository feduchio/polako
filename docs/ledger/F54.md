# F54 — a check result that is not evidence about the project must not be recorded as one

**Status:** FROZEN, revision 3. **Base:** HOST `ef11a00`.
**Finding:** 54 in `docs/ledger/B-selfhost-remaining.md`. **Origin:** P2.3.
**Goal:** G2. **Process:** v3.

This is the first production change since the P1 block. It implements **one** of the finding's two
halves — the one the finding calls non-optional.

## The defect, in one sentence

`runChecks` persists an environment failure as the project's check status, so the first external
project Polish ever targeted got a baseline saying `test`, `lint` and `build` all fail on a
repository whose suite passes.

## Scope, revision 3 — both halves. User decision 2026-09-14

Revisions 1 and 2 implemented only the refuse-to-record half and said installing was a separate
decision. **The first review round showed why that split does not hold.** The guard sends the run
to `NEEDS_HUMAN` telling the operator to install dependencies, but every baseline attempt creates a
*fresh* git worktree, which never carries `node_modules` — so the instruction cannot be acted on
and the run is a dead end. A refusal nobody can clear trades a false baseline for a stuck run.

The user chose to do the install half now. So this item is both:

1. **Make a trusted baseline obtainable** — install the project's dependencies in the sandbox
   before its checks run.
2. **Refuse to record anything untrustworthy** — the original half, which stays as the backstop
   for when install is disabled, fails, or does not help.

The order matters: the second is what makes the first safe to have. An install step alone would
persist the same false result the moment installing failed.

## Mandatory clauses

**MC1 — one predicate, one definition.** The condition "this command's result is not evidence about
the project" is defined **once** and used by both the check runner and the reproduction path, which
already has its own copy in `missingInstalledDependencies` (`src/findings/reproduce.ts:207-216`).
Two definitions of the same condition is how this defect survived: the reproduction path refused to
draw a conclusion from exactly this state while the baseline path drew one.

The condition is: the working directory contains a `package.json`, contains **no** `node_modules`,
and **either** the manifest declares at least one dependency — `dependencies`, `devDependencies`,
`optionalDependencies` or `peerDependencies` — **or** the command or the resolved script names
something that needs installed packages. It does not inspect output text. Deciding it from the
filesystem rather than from stderr is deliberate: `sh: oxlint: command not found` is a message, not
a contract, and a locale or a tool change would move it.

**Revision 2, and why the rule changed before any of it shipped.** Revision 1 said the trigger was
"argv[0] is a Node package manager". The test suite falsified that immediately — 13 failures —
and the counter-example is in the tree: `fixtures/resume-dup-fetch` declares **no** dependencies
and its check is `pnpm run test` → `node --test tests/retryFetch.test.mjs`, which needs no
`node_modules` at all. Under revision 1 every fixture run would have refused to baseline. The
declared-dependency test separates the two cases exactly: the fixture declares nothing, `unjs/defu`
declares eleven devDependencies and has none installed. This is an amendment forced by a
counter-example, not a criterion tuned to a desired answer, and it is recorded here rather than
applied silently.

**MC2 — the residual false positive, accepted and stated.** A project that declares dependencies,
does not actually need them for a given check, and whose check legitimately fails is still
classified as untrusted. That is the fail-closed direction: the system declines to state something
it cannot support rather than stating something false. Revision 1's version of this clause was far
broader; the class is now narrow, and it is recorded as a known cost rather than discovered later.

**MC3 — the untrusted result is `error`, and carries no `failureFingerprint`.** `CheckStatus`
already distinguishes `error` from `fail` (`src/domain/checks.ts:18`), so no schema widening is
needed and `fail` keeps meaning "the project's check failed". The **absence of the fingerprint is
load-bearing, not tidiness**: a fingerprint is the handle by which `compareToBaseline` asserts that
two failures are the same one, and `src/domain/checks.ts:122-127` already records a
`diagnosticChange` when a fingerprint is missing. Withholding it makes the comparison fail closed
and removes the equality that gives finding 54 its teeth.

**MC4 — `BASELINING` refuses to record.** When any check of the baseline run is untrusted, the
driver appends **no** `baseline.snapshotted` event and transitions to `NEEDS_HUMAN` with a
`terminalReason` that names the affected checks and the condition. A baseline is the thing every
later comparison is relative to; a partial or a guessed one is worse than none.
`RUN_PHASE_TABLE` already permits `BASELINING → NEEDS_HUMAN` (`src/domain/run.ts:37`), so no
transition is added.

**MC5 — the reason is named honestly.** `TerminalReasonSchema` has no code for this condition and
none of the existing ones fits: it is not `internal_error`, not `product_decision_required`, not
`repeated_failure`. A new member is added rather than an existing one bent, because calling this
condition something it is not would repeat the defect the item exists to fix. No consumer switches
exhaustively over that enum, so the addition is additive.

**MC6 — nothing else changes.** `compareToBaseline`, `hasRegression` and the `passed` fold in
`runIndependentGates` are **not** touched. The candidate and integration paths keep their current
semantics; the only difference they see is that an untrusted check now arrives as `error` without a
fingerprint, which the existing degradation ranking already handles.

**MC7 — observed by checks that fail without the change.** At minimum: a project with a
`package.json`, no `node_modules` and a package-manager check reaches `NEEDS_HUMAN` with the new
reason and appends no `baseline.snapshotted`; the same project with `node_modules` present
baselines normally; an untrusted result is `error` with no `failureFingerprint`; and a genuine
project failure with dependencies installed is still `fail` **with** a fingerprint, so the guard
has not swallowed the normal path.

## Mandatory clauses added in revision 3

**MC8 — the install command has one definition, shared with the policy that admits it.** It is
derived from the discovered package manager, lives beside the predicate in `src/shared/`, and is
admitted to `CommandPolicy.forProject` as an **exact** match for that package manager only. The
allowlist does not gain a prefix rule, and no other command becomes admissible.

**MC9 — install runs only where a check is about to run and only when the guard fires.** Both
production sites that run project checks prepare dependencies first: the `BASELINING` driver and
candidate gating. A run that can baseline must also be able to gate, or the fix moves the wall
rather than removing it. When dependencies are already available nothing is attempted, so **no
existing path changes** — every in-tree fixture declares no dependencies and is untouched.

Two config fields on `SandboxConfigSchema`: `installDependencies` (default `true`) and
`installTimeoutMs`. The default is `true` because the refusal is otherwise unclearable; `false`
is for an operator who would rather have the refusal than the install.

**MC10 — a failed install is not a project failure.** If install is disabled, fails, or leaves
dependencies still unavailable, the refusal path takes over and the terminal reason distinguishes
those cases in its summary. The install's own output is persisted as forensics, not as a check
result: it is not one of the project's checks.

## Corrections required by review round 1

**MC11 — only a non-passing result can be untrusted.** Revision 2 evaluated the predicate
independently of the results, so a project declaring dependencies whose checks **passed** was
refused. A check that passed is evidence, whatever the environment looked like.

**MC12 — the classification applies to a failure to spawn, too.** The untrusted branch sat only in
the successful-`run` path, so a sandbox throwing `ENOENT` still produced a fingerprint.

**MC13 — the resolved script text reaches the predicate.** Profile checks are
`<pm> run <script>`, and the script's text is what says whether packages are needed. Without it the
command-shape disjunct never fires for a profile check, which left the original defect survivable
for a project that declares no dependencies but whose script needs them.

**MC14 — availability, not a local directory.** `node_modules` in the check's own directory is not
the availability signal: Node resolution walks ancestors, so a workspace package legitimately has
none, and Yarn PnP projects have none at all. The test walks upward for the declared dependency and
treats a PnP marker as available.

**MC15 — AC1 is amended, not quietly broken.** The reproduction path's decision boundary **does**
change: a runnable reproduction in a project that declares unavailable dependencies now returns
`UNCERTAIN` where it previously executed. That is the same fail-closed direction and it is the
point of sharing one definition, but revision 2's AC1 claimed the behaviour was unchanged and that
claim was false. Recorded as a deliberate change.

## Acceptance criteria

1. One exported predicate, used by the check runner and by the reproduction path. Its effect on the
   reproduction path is **recorded** per MC15, not claimed to be nil.
2. An untrusted check is `error` with no `failureFingerprint`.
3. A baseline run containing an untrusted check appends no `baseline.snapshotted` and reaches
   `NEEDS_HUMAN` with a reason naming the checks.
4. A normal baseline is unaffected: same events, same statuses, same fingerprints.
5. The deliberate false positive of MC2 is stated in the code where the predicate is defined.
6. Finding 54 is updated to record what was fixed.
7. A run whose dependencies are missing installs them and baselines successfully, observed end to
   end rather than by unit: this is the clause the first review round showed was missing, because
   the refusal was unclearable.
8. With `installDependencies: false`, the same project refuses and says so in its terminal reason.
9. A project whose checks pass is never refused, even when it declares dependencies.
10. A spawn failure in an untrusted environment carries no fingerprint.
11. A profile check whose script needs packages is untrusted even when the manifest declares none.
12. A workspace package whose dependency resolves from an ancestor `node_modules` is not refused.

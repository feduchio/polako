# F54 — a check result that is not evidence about the project must not be recorded as one

**Status:** FROZEN, revision 8. **Base:** HOST `ef11a00`.
**Finding:** 54 in `docs/ledger/B-selfhost-remaining.md`. **Origin:** P2.3.
**Goal:** G2. **Process:** v3.

This is the first production change since the P1 block. It implements **one** of the finding's two
halves — the one the finding calls non-optional.

## The defect, in one sentence

`runChecks` persists an environment failure as the project's check status, so the first external
project Polish ever targeted got a baseline saying `test`, `lint` and `build` all fail on a
repository whose suite passes.

## Scope, revision 3 — both halves. User decision 2026-09-14

Revisions 1 and 2 implemented only the refuse-to-record half and said installing was a separate
decision. **The first review round showed why that split does not hold.** The guard sends the run
to `NEEDS_HUMAN` telling the operator to install dependencies, but every baseline attempt creates a
*fresh* git worktree, which never carries `node_modules` — so the instruction cannot be acted on
and the run is a dead end. A refusal nobody can clear trades a false baseline for a stuck run.

The user chose to do the install half now. So this item is both:

1. **Make a trusted baseline obtainable** — install the project's dependencies in the sandbox
   before its checks run.
2. **Refuse to record anything untrustworthy** — the original half, which stays as the backstop
   for when install is disabled, fails, or does not help.

The order matters: the second is what makes the first safe to have. An install step alone would
persist the same false result the moment installing failed.

## Mandatory clauses

**MC1 — one predicate, one definition.** The condition "this command's result is not evidence about
the project" is defined **once** and used by both the check runner and the reproduction path, which
already has its own copy in `missingInstalledDependencies` (`src/findings/reproduce.ts:207-216`).
Two definitions of the same condition is how this defect survived: the reproduction path refused to
draw a conclusion from exactly this state while the baseline path drew one.

The condition is about **reachability**, not about a directory existing. The working directory
contains a `package.json`, and **either** the manifest declares packages in `dependencies` or
`devDependencies` and **not every one of them** resolves from that directory, **or** it declares
none and the command or resolved script names a runner that does not resolve either. Resolution
walks upward as Node's does, and a Plug'n'Play marker counts as resolved. It does not inspect
output text: `sh: oxlint: command not found` is a message, not a contract, and a locale or a tool
change would move it.

Three parts of that are load-bearing and each was learned from a counter-example, recorded in
MC14 and in revision 3's corrections: **every** rather than any declared package, because a
partial install is the defect's own shape; ancestors rather than the local directory, because a
workspace package legitimately has no `node_modules` of its own; and `optionalDependencies` and
`peerDependencies` excluded, because either may be legitimately absent after a correct install.

**Revision 2, and why the rule changed before any of it shipped.** Revision 1 said the trigger was
"argv[0] is a Node package manager". The test suite falsified that immediately — 13 failures —
and the counter-example is in the tree: `fixtures/resume-dup-fetch` declares **no** dependencies
and its check is `pnpm run test` → `node --test tests/retryFetch.test.mjs`, which needs no
`node_modules` at all. Under revision 1 every fixture run would have refused to baseline. The
declared-dependency test separates the two cases exactly: the fixture declares nothing, `unjs/defu`
declares eleven devDependencies and has none installed. This is an amendment forced by a
counter-example, not a criterion tuned to a desired answer, and it is recorded here rather than
applied silently.

**MC2 — the residual false positive, accepted and stated.** A project that declares dependencies,
does not actually need them for a given check, and whose check legitimately fails is still
classified as untrusted. That is the fail-closed direction: the system declines to state something
it cannot support rather than stating something false. Revision 1's version of this clause was far
broader; the class is now narrow, and it is recorded as a known cost rather than discovered later.

**MC3 — the untrusted result is `error`, and carries no `failureFingerprint`.** `CheckStatus`
already distinguishes `error` from `fail` (`src/domain/checks.ts:18`), so no schema widening is
needed and `fail` keeps meaning "the project's check failed". The **absence of the fingerprint is
load-bearing, not tidiness**: a fingerprint is the handle by which `compareToBaseline` asserts that
two failures are the same one, and `src/domain/checks.ts:122-127` already records a
`diagnosticChange` when a fingerprint is missing. Withholding it makes the comparison fail closed
and removes the equality that gives finding 54 its teeth.

**MC4 — `BASELINING` refuses to record.** When any check of the baseline run is untrusted, the
driver appends **no** `baseline.snapshotted` event and transitions to `NEEDS_HUMAN` with a
`terminalReason` that names the affected checks and the condition. A baseline is the thing every
later comparison is relative to; a partial or a guessed one is worse than none.
`RUN_PHASE_TABLE` already permits `BASELINING → NEEDS_HUMAN` (`src/domain/run.ts:37`), so no
transition is added.

**MC5 — the reason is named honestly.** `TerminalReasonSchema` has no code for this condition and
none of the existing ones fits: it is not `internal_error`, not `product_decision_required`, not
`repeated_failure`. A new member is added rather than an existing one bent, because calling this
condition something it is not would repeat the defect the item exists to fix. No consumer switches
exhaustively over that enum, so the addition is additive.

**MC6 — nothing else changes.** `compareToBaseline`, `hasRegression` and the `passed` fold in
`runIndependentGates` are **not** touched. The candidate and integration paths keep their current
semantics; the only difference they see is that an untrusted check now arrives as `error` without a
fingerprint, which the existing degradation ranking already handles.

**MC7 — observed by checks that fail without the change.** At minimum: a project with a
`package.json`, no `node_modules` and a package-manager check reaches `NEEDS_HUMAN` with the new
reason and appends no `baseline.snapshotted`; the same project with `node_modules` present
baselines normally; an untrusted result is `error` with no `failureFingerprint`; and a genuine
project failure with dependencies installed is still `fail` **with** a fingerprint, so the guard
has not swallowed the normal path.

## Mandatory clauses added in revision 3

**MC8 — the install command has one definition, shared with the policy that admits it.** It is
derived from the discovered package manager, lives beside the predicate in `src/shared/`, and is
admitted to `CommandPolicy.forProject` as an **exact** match for that package manager only. The
allowlist does not gain a prefix rule, and no other command becomes admissible.

**MC9 — install runs only where a check is about to run and only when the guard fires.**
*Superseded by MC16 in revision 4, which names the same requirement in terms of the thing that must
hold rather than the call sites that must remember it. Kept for the record:* both production sites
that run project checks prepare dependencies first: the `BASELINING` driver and candidate gating. A
run that can baseline must also be able to gate, or the fix moves the wall rather than removing it.
When dependencies are already available nothing is attempted, so **no existing path changes** —
every in-tree fixture declares no dependencies and is untouched.

Two config fields on `SandboxConfigSchema`: `installDependencies` (default `true`) and
`installTimeoutMs`. The default is `true` because the refusal is otherwise unclearable; `false`
is for an operator who would rather have the refusal than the install.

**MC10 — a failed install is not a project failure.** If install is disabled, fails, or leaves
dependencies still unavailable, the refusal path takes over and the terminal reason distinguishes
those cases in its summary. The install's own output is persisted as forensics, not as a check
result: it is not one of the project's checks.

## Corrections required by review round 1

**MC11 — only a non-passing result can be untrusted.** Revision 2 evaluated the predicate
independently of the results, so a project declaring dependencies whose checks **passed** was
refused. A check that passed is evidence, whatever the environment looked like.

**MC12 — the classification applies to a failure to spawn, too.** The untrusted branch sat only in
the successful-`run` path, so a sandbox throwing `ENOENT` still produced a fingerprint.

**MC13 — the resolved script text reaches the predicate.** Profile checks are
`<pm> run <script>`, and the script's text is what says whether packages are needed. Without it the
command-shape disjunct never fires for a profile check, which left the original defect survivable
for a project that declares no dependencies but whose script needs them.

**MC14 — availability, not a local directory.** `node_modules` in the check's own directory is not
the availability signal: Node resolution walks ancestors, so a workspace package legitimately has
none, and Yarn PnP projects have none at all. The test walks upward for the declared dependency and
treats a PnP marker as available.

**MC15 — AC1 is amended, not quietly broken.** The reproduction path's decision boundary **does**
change: a runnable reproduction in a project that declares unavailable dependencies now returns
`UNCERTAIN` where it previously executed. That is the same fail-closed direction and it is the
point of sharing one definition, but revision 2's AC1 claimed the behaviour was unchanged and that
claim was false. Recorded as a deliberate change.

## Corrections required by review round 2 — revision 4

**MC16 — preparation is a property of running checks, not a favour three call sites do.**
`runChecks` prepares the sandbox itself, and **omitting the option means prepare with defaults**.
No caller opts in; the only way not to install is `enabled: false`, which is a refusal and not a
skip, because the checks still do not get to speak.

This replaces MC9, and the reason is a mutant the second lane found: `prepareDependencies` was an
*optional* field that `runGates` skipped when unset, so deleting the four-line assignment in
`resolveGates` left **93 tests green** while candidate gating silently stopped preparing. That is
the sixth consumer of one idea to forget it. MC9 named two places that must remember; the thing
that must actually hold is that *nothing produces a `CheckResult` from a sandbox nobody prepared*,
and the only formulation of that which cannot be forgotten puts the step inside the function that
runs the commands. The wiring at a call site now carries the operator's **setting** only; deleting
it loses the setting, not the step.

**MC17 — the refusal is decided by the results, not before them.** `runChecks` runs the checks even
when preparation failed, and refuses afterwards, when a non-passing check is untrusted — throwing
`EnvironmentNotReadyError`, which carries the results and the preparation outcome. Refusing earlier
is simpler and wrong: it re-breaks MC11, because a project that declares dependencies it does not
need for a check that **passes** would be refused, and that check is evidence whatever the
environment looked like. Only the results can answer whether this sandbox spoke about the project.

A consequence worth stating: the error type lives in `src/project/checkRunner.ts`, beside the throw,
and `engine/candidates.ts` re-exports it. Baselining, candidate gating and the integration workspace
then get the *same* refusal without three layers agreeing to it separately.

**MC18 — a candidate discarded for its environment says so.** `Candidate.error` exists precisely so
a discard is not mistaken for infrastructure noise; a gate checkout that could not produce evidence
now fills it, so that discard is distinguishable from a discard for budget.

## Corrections required by review round 3 — revision 5

**MC19 — an install sits between reading the candidate and trusting the checkout.** Revision 5
said "prepare before anything is verified" and revision 6 has to be more exact, because both
neighbours of that step matter and they pull in opposite directions.

*Before the install*, `runIndependentGates` reads what the candidate did — changed files, the diff,
the manifest hashes. An install writes an untracked `node_modules`, and a repository is entitled not
to ignore it; asking git afterwards hands installed dependency files to the silencing detector as
the candidate's own work, and one `it.skip` inside a dependency accuses the candidate of muting a
test.

*After the install*, acceptance artifacts are materialized and verified, and the checks run. An
install runs the project's own lifecycle scripts, so materializing first would put canonical bytes
where the install can still replace them, and the checks would run against the replacement. In that
order the materializer *repairs* what an install overwrote — so the invariant is not "an overwrite
fails the gate" but **the commands see canonical bytes, and verification is of what is on disk when
they run**. When materialization does not restore the file, **no check runs**: the artifacts are
what the checks exist to exercise, so a result produced against a file already called `modified`
describes something else. The gate fails with the problem and an empty check set.

*After the checks*, revision 7 adds: the tree is read once more, **tracked files only**, and the
silencing detector sees both captures. Reading the candidate early answers who did what; it cannot
see the two other parties that write to a checkout during a gate — the install's lifecycle scripts
and the check commands themselves. A `vitest.config.ts` exclusion added by either silences tests
exactly as well as one the candidate committed. Tracked-only, because by then the largest untracked
thing in the checkout is the `node_modules` we installed. The same tracked edit appears in both
captures and is reported once.

**Revision 8 makes the merge exact.** Each capture is parsed **on its own** and the findings are
merged afterwards. The detectors carry per-file state — whether a hunk only added lines, whether a
test body was substantially deleted — so one parser given two states of a file lets a deletion in
the earlier one cancel a wrap in the later one, and the silencing disappears. And a settled read
that **fails** is not a settled read: a git object that has the method and throws has failed to
answer, and the gate refuses. Only an absent method falls back, which is what a test stub is.

**Both call sites, and exactly one install**: `runChecks` prepares unconditionally too, and
preparation is memoized *as the in-flight promise* per sandbox handle. Memoizing the settled result
instead would let two concurrent askers both find nothing cached and start two package managers in
one checkout. Neither call site may be the only one, which is what makes this different from the
MC9 shape it replaced.

**MC20 — the shared definitions are observed where they are shared.** MC1 and MC8 say the predicate
and the install command have one definition each, used by the check runner, the reproduction path
and the policy that admits the command. Each of those consumers is observed by a test that fails if
the sharing is undone — including every package manager the runner can drive, since a policy that
admits a command the runner cannot issue, or the reverse, is the same defect in the other direction.

## Acceptance criteria

1. One exported predicate, used by the check runner and by the reproduction path. Its effect on the
   reproduction path is **recorded** per MC15, not claimed to be nil.
2. An untrusted check is `error` with no `failureFingerprint`.
3. A baseline run containing an untrusted check appends no `baseline.snapshotted` and reaches
   `NEEDS_HUMAN` with a reason naming the checks.
4. A normal baseline is unaffected: same events, same statuses, same fingerprints.
5. The deliberate false positive of MC2 is stated in the code where the predicate is defined.
6. Finding 54 is updated to record what was fixed.
7. A run whose dependencies are missing installs them and baselines successfully, observed end to
   end rather than by unit: this is the clause the first review round showed was missing, because
   the refusal was unclearable.
8. With `installDependencies: false`, the same project refuses and says so in its terminal reason.
9. A project whose checks pass is never refused, even when it declares dependencies.
10. A spawn failure in an untrusted environment carries no fingerprint.
11. A profile check whose script needs packages is untrusted even when the manifest declares none.
12. A workspace package whose dependency resolves from an ancestor `node_modules` is not refused.

Added in revision 4:

13. A caller that says nothing about preparation still gets a prepared sandbox, observed by the
    install command being issued before the check command.
14. A candidate whose checks **pass** in an unpreparable checkout is gated normally, not discarded.
15. The operator's `sandbox.installDependencies` reaches candidate gating, observed by a refusal
    that names the disabled case rather than an attempted install.
16. A candidate discarded because its checkout produced no evidence carries the reason.

Added in revision 5:

17. An install that replaces an acceptance artifact does not reach the checks: the command observes
    the canonical bytes, and when materialization does not restore them the gate fails it
    `modified`. Revision 5 stated this as "the gate fails", which was false against the production
    materializer and true only against a no-op test double; corrected in revision 6.
18. The reproduction path is observed to use the shared predicate, by a case where a local
    `node_modules`-exists test would have executed and the shared one refuses.
19. `tsx` and Bun are each observed — the runner-shape pattern, the install command, and the
    exact-match policy rule that admits it.

Added in revision 6:

20. An installed `node_modules` in a repository that does not ignore it produces no silencing
    finding, observed on a real git worktree rather than a mock.
21. Two concurrent check runs on one sandbox issue one install.

Added in revision 7:

22. A tracked config rewritten **by the install** and one rewritten **by a check command** are both
    caught as silencing, on a real git worktree.
23. When an acceptance artifact is not verifiable, the gate returns before any check command runs.

Added in revision 8:

24. A deletion in the candidate's capture does not cancel a wrap in the settled capture.
25. A settled read that throws refuses the gate rather than falling back to the commit-range diff.

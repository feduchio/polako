cannot invent eligibility, and both are asserted.

## How the joins are made, so a second implementer gets the same numbers

One population decides everything, and nothing is classified by its own timestamp.

0. The **`review_executions` row is the identity**, not the event payload. A review event speaks
   for an execution only when it names a row that exists and shares its run; the axis then comes
   from the row. A payload that disagrees is counted as an inconsistency and not followed.
1. An **execution** is bucketed by the `ts` of the `review.finished` event that recorded it (MC1).
   With no `review.finished` it is `unfinished` if a `review.started` exists and `unattributed` if
   neither does.
2. A **finding** inherits its execution's bucket, joined exactly: `raiseFinding` appends
   `finding.raised` with `causedBy` set to the review execution's id
   (`src/engine/reviewDrivers.ts:866-867`, `:1240-1251`), which lands in `event_causes`. A finding
   raised after the cut-off from a pre-cut-off execution was still parsed by the broken parser, so
   it is ineligible. Exactly one execution cause is required; zero or several is `unattributed`.
3. **Validations and tasks** follow their finding.
4. A **reviewer `model.call`** is attributed by `docs/PLAN.md` §1's rule — scan `events` in
   `(run_id, seq)` order and attribute the call to the execution opened by the most recent preceding
   `review.started` for that `(runId, axis)` — and then inherits that execution's bucket. A call
   issued before the cut-off for an eligible execution is still that execution's call. The axis
   comes from `purpose` only when `purpose` actually starts with `review_`; otherwise the call names
   no axis and is `unattributed` under its raw purpose.
5. **Triage survival** is status outside `RAW`, `DUPLICATE`, `NOTED`, or the existence of a
   validation row, which is written only for triage disposition `validate`
   (`src/findings/validator.ts:95-98`). `RAW` means triage has not run, so `RAW` is not a survivor.
6. **Tokens** are counted only from a `usage` whose fields are finite numbers. `usage: null` is a
   failed call contributing 0, per `docs/PLAN.md` §1; a usage object with a non-numeric field is
   malformed, contributes 0, and is counted as such — added naively, one string field turns every
   total in the report into a concatenated string.
7. Anything that cannot be joined is `unattributed` and reported as such. It is never eligible.
   Every dictionary keyed by data — axis, purpose, status, error kind, phase — has a null
   prototype, because those keys come from event payloads and an axis named `constructor` or
   `__proto__` silently loses its counts in a plain object.

On the real store all of these report zero: no unknown or mismatched review event, no ambiguous
cause, no malformed usage, and nothing unattributed.

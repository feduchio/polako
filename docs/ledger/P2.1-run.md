## Verdict

**`inconclusive — no post-plumbing production findings`.**

Eligible review executions: **0**. Eligible findings raised: **0**.

Per AC2 no eligible per-axis table is reported beside that verdict. A table of zeros would be a
yield of zero wearing a different hat, which is exactly what MC3 forbids.

**MC3's verdict belongs to an empty eligible *set*, and MC1 defines that set as executions — not as
findings.** The distinction is not pedantic and it decides what the next store will be told. An
eligible execution that **completed with an empty findings array** is what `finishExecution` writes
for a reviewer that found nothing, and what `skipExecution` writes for P1.1's skip. That is a
**measured zero**: one execution, no findings, tokens spent. It is yield data and must be reported
as such. Deciding MC3 on "zero findings" instead of "zero executions" would report the first real
post-fix round as an absence of rows — the same confusion MC3 exists to prevent, pointing the other
way. The Grok lane found this; five GPT rounds did not.

## Why the eligible set is empty, stated as three separate facts

The store holds 17 runs and 2,600 review executions. **11 of the 17 runs started after the cut-off,
and none of them reached `REVIEWING`.** The phases those eleven reached are `CREATED`,
`DISCOVERING_PROJECT`, `BASELINING`, `INTERPRETING_MISSION`, `DISCOVERING_MODELS`, `PLANNING`,
`EXECUTING`, `GATING`, `COMPARING`, `INTEGRATING`, `FAILED`. Two got as far as `INTEGRATING`.

So the empty eligible set is **not** "nothing has run since the fix". Runs happened; review did not.

Those eleven runs recorded **334 failed provider calls**. By error kind: `rate_limit` 191,
`not_found` 49, `bad_request` 42, `timeout` 40, `server` 10, `auth` 2. By the run phase in force
when the call failed: `EXECUTING` 211, `PLANNING` 37, `INTERPRETING_MISSION` 34,
`DISCOVERING_MODELS` 28, `FAILED` 24. Rate limiting is the largest single kind and `EXECUTING` the
largest single phase, and that is the whole claim: **143 of the 334 failures are not rate limits and
99 happened before `EXECUTING`**, so no single blocker explains these runs. An earlier draft of this
record called it "free-tier exhaustion during candidate execution"; the distribution does not
support that, and the reviewer was right to reject it.

The phase attribution is an **approximation**, stated because it is one: it is the last
`run.phase_changed` before the failed call in `(run_id, seq)` order, and ordering by `ts` instead
disagrees on **0** of the 334. The soft edge is the 24 rows attributed to `FAILED`, which are
plausibly calls still in flight when the terminal transition was appended; counting those as
`EXECUTING` would take "99 before `EXECUTING`" to 75. The claim above survives either reading,
which is why the approximation is recorded rather than refined.

**No choice of cut-off produces a surviving finding.** The whole store contains **0 rows in
`findings`** and **0 rows in `finding_validations`**, at any timestamp. Moving the cut-off earlier,
later, or removing it entirely leaves every attrition column zero, because no finding has ever been
recorded in this store.

**The verdict, however, does depend on the cut-off, and it should.** Since MC3 now turns on the

## The eligible path is exercised, because the real store cannot exercise it

Every number above comes from the ineligible population, so the eligible half of the
classification would otherwise be untested code. `node scripts/p2-1-yield.mjs --selfcheck` builds a
synthetic store **on the real schema** in a temp directory, populates all four buckets on purpose,
and asserts the classification: **52 of 52 assertions hold**. It exits non-zero on any failure. A
second synthetic store carries the shape the real store will have first — one completed eligible

cannot invent eligibility, and both are asserted.

## How the joins are made, so a second implementer gets the same numbers

One population decides everything, and nothing is classified by its own timestamp.

0. The **`review_executions` row is the identity**, not the event payload. A review event speaks
   for an execution only when it names a row that exists and shares its run; the axis then comes
   from the row. A payload that disagrees is counted as an inconsistency and not followed.
1. An **execution** is bucketed by the `ts` of the `review.finished` event that recorded it (MC1).
   With no `review.finished` it is `unfinished` if a `review.started` exists and `unattributed` if
   neither does.
2. A **finding** inherits its execution's bucket, joined exactly: `raiseFinding` appends
   `finding.raised` with `causedBy` set to the review execution's id
   (`src/engine/reviewDrivers.ts:866-867`, `:1240-1251`), which lands in `event_causes`. A finding
   raised after the cut-off from a pre-cut-off execution was still parsed by the broken parser, so
   it is ineligible. Exactly one execution cause is required; zero or several is `unattributed`.
3. **Validations and tasks** follow their finding.
4. A **reviewer `model.call`** is attributed by `docs/PLAN.md` §1's rule — scan `events` in
   `(run_id, seq)` order and attribute the call to the execution opened by the most recent preceding
   `review.started` for that `(runId, axis)` — and then inherits that execution's bucket. A call
   issued before the cut-off for an eligible execution is still that execution's call. The axis
   comes from `purpose` only when `purpose` actually starts with `review_`; otherwise the call names
   no axis and is `unattributed` under its raw purpose.
5. **Triage survival** is status outside `RAW`, `DUPLICATE`, `NOTED`, or the existence of a
   validation row, which is written only for triage disposition `validate`
   (`src/findings/validator.ts:95-98`). `RAW` means triage has not run, so `RAW` is not a survivor.
6. **Tokens** are counted only from a `usage` whose fields are finite numbers. `usage: null` is a
   failed call contributing 0, per `docs/PLAN.md` §1; a usage object with a non-numeric field is
   malformed, contributes 0, and is counted as such — added naively, one string field turns every
   total in the report into a concatenated string.
7. Anything that cannot be joined is `unattributed` and reported as such. It is never eligible.
   Every dictionary keyed by data — axis, purpose, status, error kind, phase — has a null
   prototype, because those keys come from event payloads and an axis named `constructor` or
   `__proto__` silently loses its counts in a plain object.

On the real store all of these report zero: no unknown or mismatched review event, no ambiguous
cause, no malformed usage, and nothing unattributed.

## What would make P2.1 decidable

Not a different query, and **not a finding row**. One run that reaches `REVIEWING` on the current
tree with a working provider lane is enough: the first completed post-cut-off execution makes the
eligible set non-empty, and its result is a measurement whether it returns findings or none. A
round of clean reviewers is yield data — it is the denominator the 60.0% raw false-positive figure
was missing. The blocking condition is reaching `REVIEWING` at all, which the eleven post-cut-off
runs did not. Recorded here, not scheduled as new scope.

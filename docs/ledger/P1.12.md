## Scope

Revision 2 removes a stronger condition that was not in the plan: at the

empty. Recovery must preserve the exact set, not manufacture a non-empty one.

## Mandatory clauses

**MC1 — answer is a durable resumption trigger.** A run reaching
`NEEDS_HUMAN` through the council records the supplied answer in
`answers.jsonl` and as a `run.answer_recorded` event with user actor. The answer
event causes the run to reopen the exact non-terminal phase that requested
input; the reopening event cites the answer, clears the old terminal reason,
and the normal daemon pipeline continues. Answering any other phase conflicts.

**MC2 — STOPPED is resumable; KILLED remains absorbing.** `stop` received while
the run is in `EXECUTING` reaches control `STOPPED` without changing the phase.
`resume` changes that run to `RUNNING`, clears `stopped_by_user`, and returns
with phase still `EXECUTING`; it does not execute a worker inside the resume
RPC. Existing PAUSED resume behaviour remains. KILLED does not become
resumable.

**MC3 — restart uses the same durable store.** Destroy the first service after
the run has entered `EXECUTING`, construct a fresh `DaemonService` over the
same `home`, and observe the same phase and exact persisted job-id set (which
may be empty before the first worker tick) after constructor recovery. P1.3's
broker restoration reports non-zero spend before another model call.

**MC4 — event causality and cleanup.** In every scenario, every `causedBy` id
resolves to an event in the same run. After service shutdown, no candidate or
integration worktree remains beneath that test environment.

**MC5 — real RPC boundary.** Creation, answer, stop and resume use
`DaemonService.handle`; tests do not call `RunEngine.control`, patch run
projections, seed terminal phases, or inject production dependencies.

## Acceptance criteria

1. Council ambiguity reaches `NEEDS_HUMAN`; `handle("answer", ...)` records the
   answer, reopens the requesting phase, and the run reaches `DONE`.
2. At `EXECUTING`, `handle("stop", ...)` returns `STOPPED` with phase
   `EXECUTING`; `handle("resume", ...)` returns `RUNNING` with phase
   `EXECUTING`.
3. A fresh service over the same home observes the pre-destruction
   `EXECUTING` phase, the same persisted job-id set, and non-zero restored
   broker spend.
4. All three scenarios satisfy MC4.

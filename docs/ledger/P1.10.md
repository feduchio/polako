## The defect

`buildProductionDeps` loads the protocol registry eagerly at `src/daemon/composition.ts:187`, reached
from the `DaemonService` constructor at `src/daemon/service.ts:94`. When that load throws, the daemon
dies in its constructor and the operator is told *what* went wrong but not *where*.

`ProtocolRegistry.load` (`src/protocols/loader.ts:17-41`) can fail four ways. Verified at `e45aebc`:

| # | Failure | Throw site | Carries the path? |
|---|---|---|---|
| 1 | protocols root missing or not a directory | `:19-21` `NOT_FOUND` | **yes** — `protocols root not found: ${abs}` |
| 2 | `SKILL.md` name does not match its folder | `:29-34` `INVARIANT_VIOLATION` | no |
| 3 | two folders claim the same protocol name | `:35-37` `INVARIANT_VIOLATION` | no |
| 4 | `SKILL.md` malformed | `parseSkillMarkdown`, `src/protocols/frontmatter.ts:9,15,21,23` | no |

### Two corrections to the plan's own wording

`docs/PLAN.md` P1.10 says the loader *"throws `NOT_FOUND` for a missing directory and
`INVARIANT_VIOLATION` for a duplicate or a name/folder mismatch … and **those errors do not carry the
path**."* Both halves need correcting, and neither correction is cosmetic:

1. **The `NOT_FOUND` case already carries the path** (row 1). Only rows 2, 3 and 4 lack it. An
   implementation that adds the path to row 1 is adding it twice.
2. **Row 4 is a failure class the plan does not mention at all, and part of it is not a `PolishError`.**
   `parseSkillMarkdown` throws `PolishError("INVALID_ARGUMENT", …)` for missing frontmatter, an empty
   body and unparseable YAML — but its last line is `ProtocolFrontmatterSchema.parse(parsed)`
   (`frontmatter.ts:23`), which throws a **`ZodError`**. A `ZodError` is not a `PolishError`. So the
   plan's instruction to catch *"`PolishError` from the loader"* would not fire at all for a `SKILL.md`
   whose frontmatter is well-formed YAML but fails the schema — for example one missing `kind`. The
   operator would get a raw `ZodError` with no path and no code.

This is the P1.2 lesson applied again: a claim about existing machinery has to be checked against this
tree's wiring before a design is built on it.

## Recorded departure from the plan's mechanism

`docs/PLAN.md` P1.10 specifies: *"the wrapper supplies the path, because the loader does not. Wrap the
eager load; on `PolishError` from the loader, **re-scan `protocols/*/SKILL.md`, identify the offending
entry by re-applying the loader's own name/folder check**, and rethrow …"*

**This contract departs from that mechanism and keeps its observable.** The path is attached **at the
loader's own throw sites**; the wrapper supplies the framing, the stderr line and the fail-closed
rethrow. Reasons, stated so reviewers can judge the departure rather than discover it:

- *The re-scan is a second copy of a rule that can drift from the first.* "Re-applying the loader's own
  name/folder check" means the name/folder comparison and the duplicate detection exist twice, in two
  files, with nothing forcing them to agree. When they disagree the diagnostic points at the wrong
  directory — which is worse than today's no-directory, because it is confidently wrong. This is the
  same two-merge-site shape that findings 17, 21, 22 and 25 describe and that P1.7 exists to delete.
- *The re-scan cannot attribute row 4 at all.* A `ZodError` never reaches a `PolishError` catch, and a
  re-scan that re-parsed every `SKILL.md` to find the offender would have to re-implement
  `parseSkillMarkdown`'s error handling as well.
- *The loader is where the information already is.* `skillPath` is a local variable at `loader.ts:25`.
  Nothing needs deriving.

The departure is in **how the path is obtained**, not in what the operator sees. The plan's Verify
clause is unchanged and is AC1 below.

## Mandatory clauses

**MC1 — every escape from `ProtocolRegistry.load` is a `PolishError` carrying the offending path.**
Rows 2, 3 and 4 gain `details.skillPath` = the absolute path of the `SKILL.md` being processed. Row 1
gains `details.protocolsRoot` = the absolute root. A non-`PolishError` escaping the per-entry work — a
`ZodError` is the known case — is converted to `PolishError("INVALID_ARGUMENT", …)` with the same
`skillPath`, and the original is preserved as `cause`. After this item, `load` has **no** escape path
that is not a `PolishError` with a path.

**MC2 — the original message survives.** Attaching the path must not replace the sentence saying what
was wrong. A caller must still be able to read `protocol name "x" must match directory "y"`.

**MC3 — the wrapper is at the production eager load, and it fails closed.** `composition.ts:187` is
wrapped. The wrapper writes one line to stderr and **rethrows**. It does not catch and continue, does
not return an empty registry, and does not downgrade the failure to a warning: a daemon with no
protocols composes no worker and no reviewer prompt, so continuing would turn a loud startup failure
into a silent behavioural one.

**MC4 — the message format is the plan's, extended by the reason.** Exactly:

    protocol registry failed to load: <code> at <path>: <original message>

`<code>` is the `PolishErrorCode`. `<path>` is `details.skillPath` when the error names a single
entry, and `details.protocolsRoot` — falling back to the resolved root — when it does not. The prefix
through `<path>` is the plan's line verbatim; `: <original message>` is appended because a line that
says where but not what does not let an operator act. The same string is the rethrown error's message
and the stderr line.

**MC5 — `reviewDrivers.ts:102` is not wrapped.** `createReviewingDriver`'s
`options.protocols ?? ProtocolRegistry.load(...)` fallback is unreachable in production:
`installProductionDrivers` injects `protocols: deps.protocols` (`composition.ts:356-361`). Wrapping a
path production does not take would add a second diagnostic surface for no operator benefit. It
inherits MC1's improvement for free, which is the point of fixing the loader rather than the caller.

**MC6 — no behaviour changes beyond diagnostics.** The same inputs fail and succeed as before. No
protocol that loaded at base fails now, and none that failed now loads. Error **codes** are preserved
for rows 1–3; row 4's `ZodError` becomes `INVALID_ARGUMENT`, which is a strict improvement over an
uncoded error and is the only code change in the item.

## Acceptance criteria

**AC1 — the plan's own verify clause.** A protocols directory containing a folder whose `SKILL.md`
declares a different `name` causes `buildProductionDeps` to throw a `PolishError` whose message
contains both the code `INVARIANT_VIOLATION` and that folder's **absolute** `SKILL.md` path.

**AC2 — the duplicate case.** Two folders declaring the same protocol name yield a message naming the
**second** folder's absolute `SKILL.md` path — the one being processed when the throw happens — and
the code `INVARIANT_VIOLATION`.

**AC3 — the class the plan missed.** A `SKILL.md` whose frontmatter is valid YAML but fails
`ProtocolFrontmatterSchema` produces a `PolishError` — not a `ZodError` — with code
`INVALID_ARGUMENT` and that file's absolute path. At base this escapes as a `ZodError`; asserting
`instanceof PolishError` is what discriminates the fix, and asserting `not.toThrow(ZodError)` alone
would not, because `PolishError` is also not a `ZodError`.

**AC4 — the root case is not double-prefixed.** A missing protocols root yields code `NOT_FOUND` and
the absolute root path, and the root path appears in the message **once**, not twice. Row 1 already
carried the path; this asserts MC1 did not append it again.

**AC5 — the original message survives (MC2).** The name/folder message still contains both the
declared name and the directory name.

**AC6 — the wrapper fails closed (MC3).** `buildProductionDeps` **throws**; it does not return deps
with an empty registry. Asserted by the absence of a return value, not only by the presence of a
throw: a wrapper that logged and rethrew a *different* error would pass a bare `toThrow()`.

**AC7 — the stderr line is written, once, and equals the thrown message (MC4).** With `process.stderr`
captured, exactly one line is written and it equals the rethrown error's message. Asserted for
equality, not containment: two independently formatted strings that drift are how an operator ends up
grepping for a line that no longer exists.

**AC8 — the loader's own callers inherit the path (MC5).** A direct `ProtocolRegistry.load` on a
broken directory — no wrapper involved — throws a `PolishError` with `details.skillPath` set. This is
the criterion that distinguishes fixing the loader from fixing the caller, and it is the reason the
departure above is worth its words.

**AC9 — mutation.** Each of the following must fail a **named** check: deleting the per-entry
try/catch in the loader; dropping `details.skillPath` while keeping the wrapper; making the wrapper
catch and return a fresh empty registry; making the wrapper write to stderr but not rethrow;
formatting the stderr line separately from the thrown message so the two can differ. Results recorded
in the run ledger.

## Out of scope, recorded rather than fixed

**The stderr line is invisible on the autostart path.** `autostartDaemon` spawns `polishd` with
`stdio: "ignore"` (`src/cli/client.ts:28-33`), so nothing the daemon writes to stderr reaches the
operator; they see only `polishd did not start: <connection error>` from `client.ts:47`. MC4's line is
therefore observable when `polishd` is run in the foreground, and not when the CLI starts it. This is
a **pre-existing defect of the autostart path, not of this item**, and fixing it means giving the
daemon a log file and pointing the CLI's failure message at it — a different change with its own
contract. It is recorded as **finding 48** in `docs/ledger/B-selfhost-remaining.md` by this item, and
this contract claims nothing about operator visibility on the autostart path. Stating it here so that
neither a reviewer nor a later reader mistakes AC7 for a claim that the operator sees the line.

Also out of scope: lazy loading of the registry, retry, and any change to `protocols/` contents.

## The defect

`buildProductionDeps` loads the protocol registry eagerly at `src/daemon/composition.ts:187` (`:212`
after this item), reached from the `DaemonService` constructor at `src/daemon/service.ts:94`. When that load throws, the daemon
dies in its constructor and the operator is told *what* went wrong but not *where*.

`ProtocolRegistry.load` (`src/protocols/loader.ts:17-41`) can fail four ways. Verified at `e45aebc`:

| # | Failure | Throw site | Carries the path? |
|---|---|---|---|
| 1 | protocols root missing or not a directory | `:19-21` `NOT_FOUND` | **yes** — `protocols root not found: ${abs}` |
| 2 | `SKILL.md` name does not match its folder | `:29-34` `INVARIANT_VIOLATION` | no |
| 3 | two folders claim the same protocol name | `:35-37` `INVARIANT_VIOLATION` | no |
| 4 | `SKILL.md` malformed | `parseSkillMarkdown`, `src/protocols/frontmatter.ts:9,15,21,23` | no |

### Two corrections to the plan's own wording

`docs/PLAN.md` P1.10 says the loader *"throws `NOT_FOUND` for a missing directory and
`INVARIANT_VIOLATION` for a duplicate or a name/folder mismatch … and **those errors do not carry the
path**."* Both halves need correcting, and neither correction is cosmetic:

1. **The `NOT_FOUND` case already carries the path** (row 1). Only rows 2, 3 and 4 lack it. An
   implementation that adds the path to row 1 is adding it twice.
2. **Row 4 is a failure class the plan does not mention at all, and part of it is not a `PolishError`.**
   `parseSkillMarkdown` throws `PolishError("INVALID_ARGUMENT", …)` for missing frontmatter, an empty
   body and unparseable YAML — but its last line is `ProtocolFrontmatterSchema.parse(parsed)`
   (`frontmatter.ts:23`), which throws a **`ZodError`**. A `ZodError` is not a `PolishError`. So the
   plan's instruction to catch *"`PolishError` from the loader"* would not fire at all for a `SKILL.md`
   whose frontmatter is well-formed YAML but fails the schema — for example one missing `kind`. The
   operator would get a raw `ZodError` with no path and no code.

This is the P1.2 lesson applied again: a claim about existing machinery has to be checked against this
tree's wiring before a design is built on it.

### A third correction, from round 1: the duplicate branch is dead

The GPT lane observed, and it is right, that **row 3 is unreachable**. `readdirSync` returns distinct
`entry.name` values, and `meta.name !== entry.name` throws at `:29-34` *before* `byName.has(meta.name)`
is consulted at `:35-37`. So by the time the duplicate test runs, `meta.name` equals a directory name
no earlier entry can have had. No input reaches that throw.

Two consequences, both recorded rather than acted on:

- **Revision 1's AC2 was vacuous in the same way P1.1's AC5 and P1.2's AC13 were.** It said "two
  folders declaring the same protocol name yield the second folder's path", and its fixture does
  produce that path — but through the *mismatch* branch, because a second folder claiming a name it
  does not own is a mismatch first. The check passes and has always passed; what it observes is not
  what its prose claimed. This is the fourth vacuous assertion found across three items, and the
  third found by a reviewer rather than by the coordinator re-reading. Revision 2 restates it as AC2′.
- **The dead branch is not deleted here.** Removing a defensive guard needs its own argument, and
  MC6 confines this item to diagnostics. Recorded as **finding 49**, to ride with the next item that
  touches the loader.

## Recorded departure from the plan's mechanism

`docs/PLAN.md` P1.10 specifies: *"the wrapper supplies the path, because the loader does not. Wrap the
eager load; on `PolishError` from the loader, **re-scan `protocols/*/SKILL.md`, identify the offending
entry by re-applying the loader's own name/folder check**, and rethrow …"*

**This contract departs from that mechanism and keeps its observable.** The path is attached **at the
loader's own throw sites**; the wrapper supplies the framing, the stderr line and the fail-closed
rethrow. Reasons, stated so reviewers can judge the departure rather than discover it:

- *The re-scan is a second copy of a rule that can drift from the first.* "Re-applying the loader's own
  name/folder check" means the name/folder comparison and the duplicate detection exist twice, in two
  files, with nothing forcing them to agree. When they disagree the diagnostic points at the wrong
  directory — which is worse than today's no-directory, because it is confidently wrong. This is the
  same two-merge-site shape that findings 17, 21, 22 and 25 describe and that P1.7 exists to delete.
- *The re-scan cannot attribute row 4 at all.* A `ZodError` never reaches a `PolishError` catch, and a
  re-scan that re-parsed every `SKILL.md` to find the offender would have to re-implement
  `parseSkillMarkdown`'s error handling as well.
- *The loader is where the information already is.* `skillPath` is a local variable at `loader.ts:25`.
  Nothing needs deriving.

The departure is in **how the path is obtained**, not in what the operator sees. The plan's Verify
clause is unchanged and is AC1 below.

## Mandatory clauses

**MC1 — every escape from `ProtocolRegistry.load` is a `PolishError` carrying the offending path.**
Rows 2, 3 and 4 gain `details.skillPath` = the absolute path of the `SKILL.md` being processed. Row 1
gains `details.protocolsRoot` = the absolute root. A non-`PolishError` escaping the per-entry work — a
`ZodError` is the known case — is converted to a `PolishError` with the same `skillPath`, and the
original is preserved as `cause`. **Revision 5 splits the code on that arm:** an error carrying an
errno becomes `IO_ERROR`, anything else `INVALID_ARGUMENT`. See AC10b.

**The root scan is inside the guarantee, not outside it** (restated in revision 2, because revision 1
asserted the guarantee and did not cover this). `existsSync`, `statSync` and `readdirSync` at
`loader.ts:18-23` are native file IO and fail natively: an unreadable root throws `EACCES` as a plain
`Error`. They are wrapped, and a non-`PolishError` from them becomes
`PolishError("IO_ERROR", …, { protocolsRoot })` with the original as `cause`. After this item, `load`
has **no** escape path that is not a `PolishError` carrying either `skillPath` or `protocolsRoot`.

**MC2 — the original message survives.** Attaching the path must not replace the sentence saying what
was wrong. A caller must still be able to read `protocol name "x" must match directory "y"`.

**MC3 — the wrapper is at the production eager load, and it fails closed.** The eager load in `buildProductionDeps` (`composition.ts:212`; `:187` at base) is
wrapped. The wrapper writes one line to stderr and **rethrows**. It does not catch and continue, does
not return an empty registry, and does not downgrade the failure to a warning: a daemon with no
protocols composes no worker and no reviewer prompt, so continuing would turn a loud startup failure
into a silent behavioural one.

**MC4 — the message format is the plan's, extended by the reason.** Exactly:

    protocol registry failed to load: <code> at <path>: <original message>

`<code>` is the `PolishErrorCode`. `<path>` is `details.skillPath` when the error names a single
entry, and `details.protocolsRoot` — falling back to the resolved root — when it does not. The prefix
through `<path>` is the plan's line verbatim; `: <original message>` is appended because a line that
says where but not what does not let an operator act. The same string is the rethrown error's message
and the stderr line.

**MC5′ — `src/engine/reviewDrivers.ts` is not modified by this item.** Its
`options.protocols ?? ProtocolRegistry.load(...)` fallback at `:102` is unreachable in production:
`installProductionDrivers` injects `protocols: deps.protocols` (`composition.ts:380-386`). Wrapping a
path production does not take would add a second diagnostic surface for no operator benefit, and it
inherits MC1's improvement for free — which is the point of fixing the loader rather than the caller.

**Verified by `git diff 7e5c013 <head> -- src/engine/reviewDrivers.ts` being empty.** Revision 4
replaced the previous MC5 with this one; the reasoning is in *Why MC5 became a claim about the diff*
below. That command is the whole verification: it is decidable, complete, and any reviewer can run it
in one line.

**MC6 — no behaviour changes beyond diagnostics.** The same inputs fail and succeed as before. No
protocol that loaded at base fails now, and none that failed now loads. Error **codes** are preserved
for rows 1–3. Two codes change, both from uncoded or miscoded errors and both diagnostics: row 4's
`ZodError` becomes `INVALID_ARGUMENT`, and (revision 5) a native per-entry read failure becomes
`IO_ERROR` rather than `INVALID_ARGUMENT`.

## Acceptance criteria

**AC1 — the plan's own verify clause, asserted by equality.** A protocols directory containing a
folder whose `SKILL.md` declares a different `name` causes `buildProductionDeps` to throw a
`PolishError` whose message **equals**

    protocol registry failed to load: INVARIANT_VIOLATION at <abs SKILL.md>: protocol name "feature" must match directory "bugfix"

Equality, not containment. Revision 1 asserted the prefix and the path with two separate `toContain`
calls, which left the text between them unconstrained; the round-1 reviewer killed that by changing
`at` to `near` and watching both assertions still pass. Containment of two fragments does not pin a
format.

**AC2′ — the second folder's path, through the branch that is actually reachable.** A folder whose
`SKILL.md` claims a name belonging to another folder yields that folder's absolute `SKILL.md` path and
the code `INVARIANT_VIOLATION`. The prose says *mismatch*, not *duplicate*, because the duplicate
throw is unreachable — see *The duplicate branch is dead* above. Revision 1's AC2 claimed the
duplicate branch and is **withdrawn**; no check may claim to observe an unreachable throw.

**AC3 — the class the plan missed.** A `SKILL.md` whose frontmatter is valid YAML but fails
`ProtocolFrontmatterSchema` produces a `PolishError` — not a `ZodError` — with code
`INVALID_ARGUMENT` and that file's absolute path. At base this escapes as a `ZodError`; asserting
`instanceof PolishError` is what discriminates the fix, and asserting `not.toThrow(ZodError)` alone
would not, because `PolishError` is also not a `ZodError`.

**AC4 — the root case is not double-prefixed.** A missing protocols root yields code `NOT_FOUND` and
the absolute root path, and the root path appears in the message **once**, not twice. Row 1 already
carried the path; this asserts MC1 did not append it again.

**AC5 — the original message survives (MC2).** The name/folder message still contains both the
declared name and the directory name.

**AC6 — the wrapper fails closed (MC3).** `buildProductionDeps` **throws**; it does not return deps
with an empty registry. Asserted by the absence of a return value, not only by the presence of a
throw: a wrapper that logged and rethrew a *different* error would pass a bare `toThrow()`.

**AC7 — the stderr line is written, once, and equals the thrown message (MC4).** With `process.stderr`
captured, exactly one line is written and it equals the rethrown error's message. Asserted for
equality, not containment: two independently formatted strings that drift are how an operator ends up
grepping for a line that no longer exists.

**AC8 — the loader's own callers inherit the path (MC5).** A direct `ProtocolRegistry.load` on a
broken directory — no wrapper involved — throws a `PolishError` with `details.skillPath` set. This is
the criterion that distinguishes fixing the loader from fixing the caller, and it is the reason the
departure above is worth its words.

**AC9 — mutation.** Each of the following must fail a **named** check: deleting the per-entry
try/catch in the loader; dropping `details.skillPath` while keeping the wrapper; making the wrapper
catch and return a fresh empty registry; making the wrapper write to stderr but not rethrow;
formatting the stderr line separately from the thrown message so the two can differ. Added in
revision 2, each from a round-1 finding: **unwrapping the root scan**; **changing `at` to `near` in
the wrapper's format**. (Revision 4 withdrew the second-wrapper mutant with AC11; revision 5 removes
it from this list.) Added in revision 5: **moving `readFileSync` above the per-entry `try`**, and
**converting only `PolishError` and `ZodError` in the per-entry catch**. Results recorded in the
run ledger.

**AC10b — the per-entry native failure (MC1, revision 5).** A **readable** root containing an
**unreadable** `SKILL.md` yields a `PolishError` with `details.skillPath` equal to that file and the
native error as `cause`.

**Why this was missing, and why it is one check and not an axis.** MC1 claims `load` has *no* escape
without a path — a universally quantified membership claim, which is the shape that hid eight defects
in P1.9's MC2. The per-entry `catch` has **two arms**: what `parseSkillMarkdown` and the name checks
throw, and what the native `readFileSync` throws. Only the first had an input. The re-check lane
killed nothing by reading and everything by mutating: moving the read above the `try`, or converting
only `PolishError` and `ZodError`, left all 904 checks green while a raw `EACCES` escaped. The same
lane scoped the remedy — *"one arm (native per-entry IO), not a new axis; do not add EISDIR/ELOOP as
separate checks"* — and that is what was added.

**The code changed with it.** The arm produced `INVALID_ARGUMENT`, which revision 1 specified when a
`ZodError` was the only non-`PolishError` it expected. A permission failure is not an invalid
argument, and the **root** scan already calls the identical failure `IO_ERROR`. An errno now selects
`IO_ERROR` at both levels and `INVALID_ARGUMENT` stays for content that is wrong rather than
unreadable. Telling an operator `INVALID_ARGUMENT` about file permissions is the same class of
miscommunication as finding 27 itself.

**AC10 — the root scan's native failure (MC1, revision 2).** A protocols root that exists but cannot
be read yields `PolishError` with code `IO_ERROR`, `details.protocolsRoot` equal to that root, and the
native error as `cause` — asserted both directly on `ProtocolRegistry.load` and through
`buildProductionDeps`, whose operator line must read `… IO_ERROR at <root>`. Asserted at both levels
because the loader is where the guarantee lives and the wrapper is where the operator reads it.

**AC11 — withdrawn in revision 4.** MC5′ is verified by a one-line `git diff`, which is complete. See
below.

## Why MC5 became a claim about the diff

Three rounds were spent escalating one clause, and the escalation is the finding.

| Round | Clause | How it was defeated |
|---|---|---|
| 1 | MC5, unobserved | "No check enforces the prohibition" — class (c) |
| 2 | AC11, counts the diagnostic literal | A second wrapper words its own message |
| 3 | AC11b, pins the `ProtocolRegistry.load(` lines | Wrap the *consumers*, not the load; the line is untouched |

Each fix was a tighter grep, each was defeated by moving one step outward, and there is no last step:
a wrapper can sit around the call, the statement, the function, the module, or the caller. This is the
unsatisfiable shape `docs/ledger/PHASE-C.md`'s stopping rule names — *"for any set of checks there
exists an incorrect implementation conditioned on some combination of ambient state the fixtures do
not vary"* — and B-selfhost-8's twenty-six test-only rounds are what it looks like when it is not
stopped. Revision 3 was already a test-only commit. The Grok lane said plainly: *"Do not add AC11c.
Another grep will be punched through the same way."*

The error was upstream of all three checks. **MC5 was written as a property of the tree — "no second
wrapper exists" — when what the item actually needs is a property of its own diff: "this item does not
touch that file."** The first is a universal quantification over code that could be written and cannot
be checked by any finite suite. The second is decidable by one command, completely, with no mutant
that survives it: a mutant *is* a change to that file, and the diff shows it.

So MC5′ is a diff claim and AC11 is withdrawn, taking both source-scanning checks with it. This is a
deletion of machinery, not an addition — the G3-correct direction, and the one the round-3 lane's own
proportionality judgement asked for. What is lost is real and is stated: nothing prevents a *future*
item from adding a second wrapper. That is a review-time concern for that item, not a runtime property
this one can enforce.

## Out of scope, recorded rather than fixed

**The stderr line is invisible on the autostart path.** `autostartDaemon` spawns `polishd` with
`stdio: "ignore"` (`src/cli/client.ts:28-33`), so nothing the daemon writes to stderr reaches the
operator; they see only `polishd did not start: <connection error>` from `client.ts:47`. MC4's line is
therefore observable when `polishd` is run in the foreground, and not when the CLI starts it. This is
a **pre-existing defect of the autostart path, not of this item**, and fixing it means giving the
daemon a log file and pointing the CLI's failure message at it — a different change with its own
contract. It is recorded as **finding 48** in `docs/ledger/B-selfhost-remaining.md` by this item, and
this contract claims nothing about operator visibility on the autostart path. Stating it here so that
neither a reviewer nor a later reader mistakes AC7 for a claim that the operator sees the line.

Also out of scope: lazy loading of the registry, retry, and any change to `protocols/` contents.

## A coupling both lanes verified, recorded because it is invisible at the seam

`YAMLParseError.code` is a **string** — `BAD_INDENT`, `BLOCK_AS_IMPLICIT_KEY` — not a numeric errno.
So revision 5's discriminator would classify a raw YAML failure as `IO_ERROR`, and the only reason it
does not is that `parseSkillMarkdown` converts YAML failures to a `PolishError` **before** the
discriminator sees them. Both lanes established this independently: GPT raised it as an open note
after executing it, Grok confirmed it by deleting the conversion and watching `load` report
`IO_ERROR` with `cause.code === "BAD_INDENT"` while all 20 related checks stayed green.

Grok's recommendation, taken verbatim: **comment the dependency; do not tighten the discriminator;
do not add a YAML acceptance criterion.** Tightening without a failing input would be a production
change with nothing driving it, and a YAML check would be a new content axis after the scoping the
same lane asked for and got — one input per *arm*, not one per errno value. The comment is at
`src/protocols/loader.ts`.

**Process note, stated rather than buried:** that comment was written **after** both lanes returned
clean on `98ca1b6`, so the reviewed artefact is `98ca1b6` and the delta is a comment naming a
dependency both lanes had already executed and agreed on. It changes no behaviour. Recorded here
because process v3 requires both lanes clean on the *same* commit, and this is the one place in this
item where the letter of that rule and its purpose came apart.

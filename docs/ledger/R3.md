# R3 — A run that stops says why

**Plan:** `docs/RECOVERY.md` §3 R3, and finding 55. **Base:** `f66d3af`.
**Reviewer lane:** GPT (`gpt-5.6-sol-high`), one lane.

## Defect (normative)

`handleZeroSurvivors` (`src/engine/candidateDrivers.ts`) returned `{ nextPhase: "FAILED" }` with no
`terminalReason`, so:

```
polish status run_01m2gy5yg30631j247sn13 --json   # D1
"terminal": null
```

and the same for `run_01m2h2vmy5qj0648tcn2fn` and `run_01m2h3ck0v06t7596n0fh7`. Three runs, three
absent reasons. An operator cannot tell a run whose work failed its gates from a run where no work
was ever done — and in all three it was the second, because every candidate was refused by the
provider before it produced anything:

```
sqlite3 "file:$HOME/.polish/polish.db?mode=ro" \
  "select json_extract(json,'$.payload.candidate.state'), count(*) from events
    where run_id='run_01m2gy5yg30631j247sn13' and type='candidate.state_changed' group by 1;"
DISCARDED | 22     # every one, with `ProviderError: rate limited … openrouter_free_tier_daily`
```

Two further shapes were observed while running R0 and are the same defect elsewhere:

- A driver error in a council phase pauses the run (`engine.ts:230`) and is then rethrown without
  being recorded (`:235`). The daemon is spawned with `stdio: "ignore"` (`src/cli/client.ts:28`),
  so the error reaches no event and no log. `run_01m2h3hpe2f6f4ra1ywcg7` sat in `PLANNING/PAUSED`
  for 11.3 minutes with `actor: {"kind":"user"}` on the pause and no cause available anywhere.

## Required end state

1. `handleZeroSurvivors` never returns a terminal phase without a reason.
2. The reason distinguishes **nothing ran** from **the work lost**. A provider that refused every
   candidate has judged nothing, and its allowance lifts on its own, so that case asks a human
   rather than terminating: `provider_budget_exhausted`, a code of its own so it is countable.
   Work that reached a gate and failed stays `repeated_failure`.
3. `GATING → NEEDS_HUMAN` becomes a legal edge, for (2). `COMPARING` already has it.
4. A driver error records an event before anything else happens to the run, so the cause survives
   whatever the engine does next.

## Acceptance checks

1. A task at its attempt cap whose candidates were all discarded with a provider error reaches
   `NEEDS_HUMAN` with code `provider_budget_exhausted`, and the summary names how many were refused
   and quotes the provider's own words.
2. The same task whose candidates reached a gate and failed reaches `FAILED` with
   `repeated_failure`, and the summary says the gates failed.
3. A discard that is neither judged nor a provider refusal still produces a reason — never `null` —
   and the summary carries the recorded discard text.
4. A driver error appends `run.driver_failed` carrying the phase and the error, before the run is
   paused.
5. Gate green at Node 24.

## Non-goals

- Making the daemon's stderr reach a file. Worth doing, not this item: the fix here is that the
  cause is in the run's own event log, where `polish log` already looks.
- Retrying or waiting out an exhausted allowance automatically. R1c.
- The other two `terminalReason: null` paths, if any exist beyond those observed. This item repairs
  what three runs demonstrated.

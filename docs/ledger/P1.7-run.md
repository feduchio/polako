## What shipped

`DaemonService.resolveRunSettings(runId) → { config, budget, overrides }` is the single resolution of
a run's settings, read by all three consumers: the engine's `resolveRunConfig`, the broker's
`BudgetTracker`, and `composition.ts`'s `resolveCliBudget`. `applyRunBudgetOverrides` and
`withRuntimeValidationMode` each have exactly one production call site. The two per-run caches are
one. Findings 12 (settings half), 17, 21, 22 and 25 are closed.

- **17**: neither boundary defaults. `cli/index.ts` sends no `runtime` key when the flag is absent,
  `service.handle` passes `null`, and only `createRun` turns `null` into the configured mode — once,
  persisting the resolved value, so editing `polish.toml` cannot move a run already in flight.
- **21**: `run.settings_fallback` carries joined reasons, the requested mode and the effective one,
  once per run. Fallback stays per dimension; the event records what was discarded, not more.
- **22**: both source-grep pins retired. What they reached for is observed behaviourally — a mutant
  writing `this.config.runtimeValidation.mode = mode` fails **eight** named isolation checks.

## Round 1: the item shipped the defect its own contract described

Finding 17's text, in the contract, says: *"Fixing only the CLI leaves the RPC defaulting; fixing only
the RPC leaves the CLI sending `auto`. …AC2 and AC3 assert the two boundaries separately."*

Revision 2 then shipped an AC3 that did not exist. The CLI checks that were there asserted
`mocked.mock.calls.map((call) => call[0])` — the RPC **method name** — so restoring
`flag(args, "--runtime") ?? "auto"` passed all of them. Both lanes found it, independently, in the
same round. So did the second finding: MC3 said the RPC accepts `string | null | absent`, and
`optionalString` throws on anything non-string, so an explicit `null` was a `CONFIG_ERROR` and no
non-CLI client could say "unspecified".

Writing down why a check is needed does not produce the check. Both of these were stated correctly in
the contract and absent from the implementation, and the contract's own words are what let the
reviewers find them quickly.

## Round 2: one value is not a predicate

AC3b asserted `runtime: 7` is rejected. The GPT lane replaced `nullableString`'s
`value === undefined || value === null` with `if (!value) return null` — the natural simplification —
and all 927 checks passed, because `7` is truthy. Under that mutant `""`, `false` and `0` all silently
mean "unspecified" and take the configured mode.

AC3b now enumerates them. The general shape, which is worth carrying: **a criterion that names one
representative of a class does not observe the predicate that defines the class.** This is the same
error as P1.9's first AC8 and P1.10's first AC1 — a check that passes for the right reason on the
input its author chose, and for the wrong reason on the input they did not.

## A reviewer claim the coordinator rejected, and both lanes then confirmed

Round 1's Grok lane reported that `options.resolveRunSettings?.(runId).budget` throws when the
resolver is omitted. It does not: optional chaining short-circuits the **entire** chain, so the
expression evaluates to `undefined`. The coordinator rejected the note rather than acting on it; the
GPT lane verified by execution in round 2 and Grok verified its own note in round 3 and withdrew it.

Recorded because the reviewers' output is not automatically correct, and the cost of acting on a false
note is a production change made for no reason. Grok's round-3 refinement is worth keeping: a resolver
that is *present* and returns `undefined` **would** throw on `.budget`. Production's always returns an
object.

## Two corrections to the plan

1. **Three consumers, not two.** `docs/PLAN.md` P1.7 names the engine and the broker.
   `composition.ts:403`'s `resolveCliBudget` is a third, and it needs the **overrides**, not the
   resolved limits, because `unusedCliMetadata` records whether the operator asked. Neither value
   derives from the other: an override equal to the configured cap resolves to the same limits as no
   override at all. AC11 is the criterion that discriminates the designs, and an implementer returning
   only `BudgetLimits` would have made `applied: false` correct-looking and wrong.

2. **The 982-line test file did not shrink by a third; it grew to 1105.** The plan predicted P1.7
   would delete *"~⅓ of a 982-line test file"*. Three cases were retired — finding 17's inverted
   expectation and the two source greps — and nine added. Grok judged the result proportionate in
   round 3 and asked that the prediction be corrected in the ledger so **P1.3 does not expect a
   slimmer file**. Corrected in `docs/PLAN.md`.

## Unblocks P1.3, and one thing found for it

`docs/PLAN.md` blocked P1.3 on this item, on an *"unexplained"* budget resolution: a corrupt facade
apparently yielding `limit: 1` while the daemon-wide budget resolved to 100.

**It is explained, and it is not an anomaly.** The test
`keeps the sound half of a run's persisted budget when the other half is corrupt` writes the facade
**twice**. Its second write is `{ ...metadata, budgetTokens: "lots" }` over the *original* metadata,
so `budgetUsd: 1` is restored and is the **sound** half. `limit: 1` is exactly right. The previous
session read the first write and reasoned about the second scenario.

The real blocker is the one the handover note gave for the other three cases: these tests restart
repeatedly on one run and rely on spend resetting to zero. Recorded in P1.3's contract.

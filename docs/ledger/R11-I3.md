# R11 I3 — task ownership

**Date:** 2026-09-25. Store checked with `sqlite3 file:~/.polish/polish.db?immutable=1`.

Task states actually stored: PENDING (created), READY, RUNNING, GATED, SELECTED, INTEGRATING, INTEGRATED, BLOCKED. No event holds `QUEUED_FOR_INTEGRATION`. Candidate states actually stored: IMPLEMENTED, PASSED_GATES, DISCARDED, WINNER. No `CREATED`, `IMPLEMENTING`, or `GATING`.

What changed:

- `TASK_TABLE` sends `SELECTED` to `INTEGRATING`. `QUEUED_FOR_INTEGRATION` is gone. `seedWinnerForTests` now marks the task `SELECTED`, which is the state production already integrated from.
- `REJECTED` and `CANCELLED` stay. Nothing has emitted them, but `terminalTask`, anti-fake-DONE, and planning re-entry all treat them as the way a task ends without integrating. Deleting the states would delete that outcome.
- Every task-state write goes through `transitionTask`. Inside the append transaction it re-reads the projected task, rejects an attempts regression with `CONFLICT`, and rejects an edge the table does not have. The three writers were `appendTaskEvent`, `promoteEligibleTasksToReady`, and `restoreIntegrationFailedForRetry`.
- `CANDIDATE_TABLE` is deleted, and so are the three candidate states that were never written. `validateTable` moved into `fsm.test.ts`; production does not call it.
- Finding status changes go through `commitFindingStatus`. A validation that the caller sees as RAW → VALID is stored as RAW → VALIDATING → VALID, because that is the path the validator took and the table has no direct edge.

## Mutants

The new tests are the kill:

- a stale `GATED` after `BLOCKED` throws `INVALID_TRANSITION` (`taskTransition.test.ts`);
- attempts 2 → 1 throws `CONFLICT`;
- `commitFindingStatus("RAW", "RESOLVED")` throws. `VALIDATING` → `VALID` does not.

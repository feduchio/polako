## The departure, and how it failed

The plan specified persisting a truncated reviewer response as a **completed** execution with an error
marker. I departed: truncation became a sticky per-model failure, on the argument that the retry was
"bounded by machinery that already exists".

**That argument was false, and both lanes found it independently in round 1.** Production
`selectReviewProviders` *excludes* sticky-failed models, so after one truncation each the pool empties,
`exhaustedAxes` never reaches `maxAxisAttemptsPerRound`, and the driver returns `waiting` forever — the
branch whose own comment calls it "the unbounded loop in a quieter form". My AC6 passed only because its
harness returned a fixed model list with no exclusion: it tested a selector the daemon does not use.

Both lanes nevertheless agreed the **classification** was right — a truncated review is not completed
work, and the plan's row would have let `isReviewRoundComplete` count it and convergence use it as
review proof. So the departure stands and only its termination story was wrong. The bound now comes from
the wait decision: transient exclusions (rate limits) justify waiting, deterministic ones (truncation,
400, schema) terminate the run with a summary naming the cap and its value.

The lesson is narrower than "don't depart from the plan". It is that a departure justified by *existing
machinery* has to be verified against the *production wiring* of that machinery, not its shape. I read
`exhaustedAxes` and stopped; I did not read the selector that feeds it.

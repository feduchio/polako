# R4 — Decomposition happens once

**Plan:** `docs/RECOVERY.md` §3 R4. **Base:** `ae8e2a1`.
**Reviewer lane:** GPT (`gpt-5.6-sol-high`), one lane.

## Defect (normative)

`createPlanningDriver` guards on `tasks.listByRun(...).length >= 1` and then **awaits**
`council.decompose`. Two drivers that both reach the guard while the list is empty both decompose
and both append. D1 did exactly that:

```
sqlite3 "file:$HOME/.polish/polish.db?mode=ro" \
  "select seq, json_extract(json,'$.payload.stage'), json_extract(json,'$.payload.decision')
     from events where run_id='run_01m2gy5yg30631j247sn13' and type='supervisor.decision';"
54  | intake    | APPROVED
62  | intake    | APPROVED
128 | decompose | APPROVED
159 | decompose | APPROVED

  "select seq, substr(json_extract(json,'$.payload.task.title'),1,40) from events
     where run_id='run_01m2gy5yg30631j247sn13' and type='task.created';"
129..133  five titles
160..164  the same five titles, different ids, same interpretation
```

The second set landed at seq 160, after the run had already advanced to EXECUTING at seq 139 — so
the second decomposition was in flight across the first one's entire life. Ten tasks, five distinct
titles: half the quota that run spent bought nothing.

The plan asks for a **durable** guarantee, not an in-memory latch: a latch dies with the process,
and a run that is recovered after a restart is exactly the case that needs it.

## Required end state

1. A claim on decomposing one interpretation is taken **before** the await and lives in the event
   log, where a restart cannot lose it and a second daemon cannot miss it.
2. A driver that already started before the claim existed does not append into a run that now has
   tasks: the task list is read again in the same synchronous step as the append.
3. A claim that produced no tasks is released. An answered `NEEDS_HUMAN` re-enters PLANNING with
   the task list still empty, and a lock nobody can release is a run that waits forever.
4. A discarded decomposition is recorded, so the waste is countable rather than silent.

Both (1) and (2) are needed, and neither replaces the other: the first is a lock, the second is the
check that does not depend on the lock having been there first.

## Acceptance checks

1. Two drivers invoked concurrently on one run create **one** set of tasks and at most one
   `decompose APPROVED`.
2. A driver that runs after the tasks exist appends none, and records why.
3. A decomposition that ends in `NEEDS_HUMAN` releases its claim: one claim, one release.
4. Gate green at Node 24.

## Non-goals

- The double `intake APPROVED` at seq 54 and 62. It is the same shape one phase earlier, and this
  item does not touch INTERPRETING_MISSION; if a run shows it costing work, it is a successor.
- Cross-process locking stronger than the event log — two daemons on one store is not a
  configuration this product supports today, and the log is what both would read.

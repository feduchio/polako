## MISSION_CRITICAL invariants

1. **Replay-safe evidence only.** A pathology sample is a deterministic projection of persisted Store records/events at a persisted observation boundary. Filesystem state, process-local counters, map iteration order, current model opinion, and unpersisted wall time are not sample inputs.
2. **Stable ordering and identity.** Source events are ordered by `(seq, id)`. Each sample has a stable key derived from `runId + boundaryEventId`; reprocessing the same boundary cannot append a duplicate sample or decision.
3. **Decision persistence before effect.** Every detector result and selected strategy is persisted with detector kind, window bounds/sample keys, evidence refs, budget snapshot, action, reason, and causal event ids before the action is executed. Recovery executes an unexecuted persisted decision; it does not decide again.
4. **Budget before recovery.** At every boundary C2 computes budget before selecting any recovery. A run that is already eligible for accepted B6 `DONE` completes `DONE` (completion is not recovery and schedules no spend). Otherwise, exhaustion makes `BUDGET_STOP` the only decision: no `CHANGE_ENSEMBLE`, rollback, review, worker, or model work may be scheduled first.
5. **No double accounting.** Tokens and known USD are folded once from unique completed `model.call` records. `budget.updated`, retries, restored snapshots, reports, and process-local `BudgetTracker` state are never second usage sources.
6. **Known cost is honest.** `costUsd: null` is not coerced to a known zero. Persist known USD separately from `unknownCostCalls`. C2 does not estimate missing provider prices or claim a USD limit is exhausted from unknown data.
7. **Wall clock survives resume.** Run elapsed time is based on persisted run start plus persisted evaluation timestamps. Restarting the daemon never resets elapsed time. Replay at a historical boundary uses that boundary timestamp; a live timeout is caused by a newly persisted clock-tick/evaluation boundary, not `Date.now()` hidden inside a pure detector.
8. **Bounded actions only.** C2 may choose only:
   - `CHANGE_ENSEMBLE`;
   - `ROLLBACK` to a proven checkpoint;
   - `NEEDS_HUMAN`;
   - `BUDGET_STOP`.
   It may not create speculative coding tasks, weaken gates, erase findings, alter user checkout state, or independently declare DONE; accepted B6 remains the sole DONE authority.
9. **Rollback safety.** A rollback target must be a persisted checkpoint for the same run, have no gate status in `{fail, error, timeout}`, and be selected through accepted B6 dominance/proven-checkpoint policy. This gate predicate is an additional C2 filter, not a replacement for B6 dominance. Rollback is applied only through B6 integration-lane/CAS rollback. No target means `NEEDS_HUMAN`, never a guessed hash.
10. **Task-origin integrity.** Style-only growth detection cannot authorize product-code work from nonblocking/UNCERTAIN findings. Existing TaskOrigin and finding-validation invariants remain authoritative.

## Canonical persisted sample

C2 introduces a versioned `PathologySample` projection/event payload containing:

- `version`, `runId`, `boundaryEventId`, `boundarySeq`, `observedAt`;
- `checkpointHash`;
- sorted finding observations keyed by stable fingerprint, including status, blocking flag, severity, checkpoint, and latest causal validation/review event;
- a canonical progress vector:
  - checkpoint hash and evidence vector;
  - integrated terminal task ids;
  - resolved VALID-blocking finding fingerprints;
  - successful gate/check fingerprints;
  - accepted corpus/evidence refs;
- disagreement set/count derived from persisted review/finding validation records, never from free-text similarity alone;
- task graph summary and ids added since the prior sample;
- typed `workClass` provenance for each task (`functional | style_only`), including its source requirement/finding ref and classification event;
- cumulative budget snapshot and source event watermark.

Arrays and record keys are sorted before hashing/persistence. Sample construction is pure for a fixed Store prefix.

### Observation boundaries

Samples are emitted only at persisted, stable boundaries relevant to convergence:

- completed review/validation round;
- checkpoint creation or rollback;
- persisted strategy execution/result;
- explicit budget evaluation tick when wall-clock exhaustion can change the decision.

Retries or daemon resume at the same boundary reuse the sample key. No sample is emitted merely because a polling loop ran.

## Sliding-window detectors

Window sizes are validated positive integer strategy knobs. A detector is silent until its full window exists. Each finding includes exact sample keys and machine-readable evidence.

1. **Finding oscillation**
   - For one stable fingerprint, the latest four (or configured `findingOscillationWindow >= 4`) observations contain two incompatible states alternating `A,B,A,B`.
   - Missing observations, duplicates, or monotonic transitions such as `RAW→VALIDATING→VALID→RESOLVED` are not oscillation.
   - The detector compares persisted status/validation outcome, not wording.
2. **Checkpoint oscillation**
   - The latest four (or configured `checkpointOscillationWindow >= 4`) checkpoint observations alternate between two distinct persisted code states `A,B,A,B`.
   - Repeated samples at one unchanged checkpoint, a linear sequence of unique checkpoints, or one deliberate rollback followed by progress are negative cases.
3. **No progress**
   - Across `noProgressAttempts` consecutive eligible samples, the canonical progress vector shows no strict improvement: no new successful gate/check evidence, no newly integrated required task, no resolved VALID-blocking finding, no accepted evidence/corpus addition, and no checkpoint evidence improvement.
   - A newly persisted, proof-bearing clean round for the current checkpoint is progress. Mere review activity, token spend, retries, new raw/UNCERTAIN findings, or code churn alone are not.
   - The detector is silent once the current Store prefix is already eligible for accepted B6 `DONE`. Thus the default `noProgressAttempts=3` composes with `requiredCleanRounds=3`.
4. **Non-shrinking disagreement**
   - `disagreementWindow >= 2`. Only completed review/validation rounds for the same checkpoint participate.
   - A set element is a finding fingerprint for which persisted structured records contain conflicting terminal positions from completed independent executions on that checkpoint: at least one `VALID` position and at least one `REJECTED` position, or an unresolved `UNCERTAIN` validation with evidence refs to both opposing completed positions. Free-text similarity cannot create membership.
   - A lone minority position still counts when there is an opposing completed position (for example a 2-of-3 split); “single dissent” means one position with no persisted opposing terminal position and is negative.
   - Across the window, the canonical unresolved disagreement set must be non-empty and not a strict subset of the first set. A strict subset, a persisted resolution, incomplete round, or single round is negative.
5. **Style-only task growth**
   - C2 introduces `TaskWorkClass = functional | style_only`, persisted in each new `task.created` payload/projection with `classifiedBy`, `sourceRef`, and `classificationEventId`. Historical/missing values default fail-safe to `functional`.
   - `workClass` is orthogonal to and cannot replace `TaskOrigin`. `style_only` is legal only for an already-legal non-investigation task with kind `simplify` or `refactor`, whose `sourceRef` is its existing `mission_requirement` or VALID-blocking-finding origin and whose structured planner/scope-guardian output explicitly classifies the work. Investigation tasks cannot be `style_only`.
   - Across `taskGrowthWindow`, the task graph grows and every added task has valid `workClass=style_only` provenance. Title/description keyword heuristics are forbidden.
   - Any added functional, missing/invalid-classification, or investigation task makes this detector silent for that window.
   - Detection is a guardrail: it cannot legalize a nonblocking/UNCERTAIN-finding coding task or weaken TaskOrigin validation.

Multiple detectors may fire at one boundary. All results are sorted by the stable Pathology enum order and persisted. Exactly one action is selected by total priority: `NEEDS_HUMAN` > `ROLLBACK` > `CHANGE_ENSEMBLE`; ties use Pathology enum order. Budget exhaustion is handled earlier and overrides this entire ordering.

## Budget accounting and precedence

The persisted C2 budget snapshot contains:

- `runTokens` and per-task tokens: sum of `inputTokens + outputTokens` from each unique `model.call` usage exactly once;
- `knownRunUsd`: sum only finite nonnegative non-null `costUsd`;
- `unknownCostCalls`: stable ids of usage-bearing calls with null/unknown USD;
- `elapsedMs`: `max(0, observedAt - run.created.ts)`;
- live `config.budget` limits used by `BudgetTracker`, plus any facade CLI metadata recorded separately as unused while B-8 remains open;
- source high-watermark and exhausted dimensions.

Rules:

1. Deduplicate by stable `callId`; if absent for legacy data, use event id. Conflicting duplicate usage for one call id fails closed to `NEEDS_HUMAN` / invariant error; it is not summed twice.
2. Failed calls with no usage add no invented usage. If a provider returns known usage for a failed attempt, it may be counted only when that usage is persisted with a unique attempt/call identity.
3. Crossing or equalling any configured token, known-USD, task-token, or wall-clock limit exhausts that dimension.
4. `CONVERGENCE_CHECK` uses this total order:
   1. accepted B6 anti-fake/state-integrity check (a failure keeps its existing fail-closed terminal);
   2. accepted B6 completion eligibility, including runtime, open-blocking, and checkpoint-bound clean-round proof — if eligible, `DONE`;
   3. budget exhaustion — if exhausted, persist `BUDGET_STOP`;
   4. C2 detector/action selection;
   5. existing B6 continue/recovery behavior when C2 selects no action.
   Thus a converged-and-exhausted prefix becomes `DONE`; an exhausted prefix requiring any further work becomes `BUDGET_STOP` before that work.
5. `BUDGET_STOP` transitions the run phase to **`FAILED`** with `terminalReason.code = "budget_exhausted"`. It does not enter `NEEDS_HUMAN`, does not rely on still-open B-13 answer/resume semantics, and does not silently mutate user control state. Already in-flight cancellation follows existing control/scheduler semantics.
6. `BudgetTracker` remains the pre-call guard for model calls. `BrokerService.restore()` and C2 must delegate to one canonical event fold; for the same Store prefix their restored snapshots must be equal. Neither maintains a competing counter.
7. C2 exhaustion uses the same live `config.budget` limits supplied to `BudgetTracker`. While B-8 is OPEN, CLI metadata overrides are recorded as unused and are not applied as a second C2-only cap.
8. For a configured wall-clock limit, run creation persists a scheduler budget-deadline job with `dueAt = run.created.ts + limit`. Activity boundaries also evaluate it. On resume after the deadline, scheduler recovery immediately appends one deduplicated budget-evaluation boundary. Its persisted timestamp is the sole live clock input.

## Strategy policy

Given non-exhausted budget:

- `finding_oscillation` → `CHANGE_ENSEMBLE`, bounded by a persisted per-pathology action count; if no eligible alternative or bound reached → `NEEDS_HUMAN`.
- `checkpoint_oscillation` → `ROLLBACK` only when accepted B6 returns a proven target; otherwise `NEEDS_HUMAN`.
- `no_progress` → first bounded `CHANGE_ENSEMBLE`; later occurrence may `ROLLBACK` to a proven dominant checkpoint; otherwise `NEEDS_HUMAN`.
- `disagreement_not_shrinking` → `CHANGE_ENSEMBLE` once when an eligible independent ensemble exists, otherwise `NEEDS_HUMAN`.
- `task_graph_growth_from_nonblocking` → `NEEDS_HUMAN`; it never auto-deletes tasks or creates cleanup work.

`CHANGE_ENSEMBLE` affects only the next review round, respects routing/cost eligibility and the accepted quality floor, and is persisted so resume cannot rotate repeatedly for one decision.

After a C2 `ROLLBACK`, the engine continues from the restored checkpoint into `REVIEWING` (or `PLANNING` only if accepted task state requires it). C2 does not transition to `SIMPLIFYING` or create C1/simplification work.

## Resume and idempotency

1. Replaying the same Store prefix yields byte-equivalent canonical samples, detector outputs, budget fold, and strategy decision.
2. A unique decision key is `(runId, boundaryEventId, decisionVersion)`, where `decisionVersion` is the constant payload schema version `1`. It never increments per retry or recovery; an existing decision for a boundary forbids any second decision under another version during C2 v1.
3. Recovery states are explicit: `decided`, `effect_started`, `effect_completed` (or equivalent event sequence).
4. If `decided` exists without completion, resume executes that exact action once.
5. If completion exists, resume is a no-op.
6. Rollback uses accepted B6 compare-and-swap/integration-lane semantics; a stale head does not create a second checkpoint and goes to `NEEDS_HUMAN`.
7. `CHANGE_ENSEMBLE` records the target review round/ensemble identity before scheduling so duplicate jobs are rejected/reused.
8. `BUDGET_STOP` is terminal/idempotent and cannot be replaced by later pathology recovery on replay.

## Deterministic acceptance checks

1. Same ordered Store prefix projected twice, including after service reconstruction, yields identical sample hashes and decisions.
2. Duplicate boundary delivery persists one sample and one strategy decision/effect.
3. Positive and false-positive-negative tests for every detector:
   - finding `A,B,A,B` positive; monotonic/missing/duplicate states negative;
   - checkpoint `A,B,A,B` positive; stable/linear/one rollback then progress negative;
   - no-progress positive only with unchanged progress vector; activity/spend alone remains no progress, while a proof-bearing current-checkpoint clean round or real gate/task/finding/evidence improvement is negative; three normal clean rounds can reach B6 DONE without no-progress;
   - disagreement 2-of-3 structured split/non-shrinking positive; shrinking/resolved/incomplete/single-position/single-round negative;
   - legal simplify/refactor tasks with typed `workClass=style_only` provenance positive; keyword-only, missing provenance, investigation, illegal nonblocking-finding, or functional growth negative.
4. Budget fold counts duplicate `model.call`/restore inputs once; token, per-task, known USD, and wall clock boundaries each exhaust at equality.
5. Null USD increments `unknownCostCalls` and never known USD.
6. Daemon restart preserves elapsed origin and cumulative usage.
7. Exhausted + B6-DONE-eligible produces `DONE`. Exhausted + not-DONE-eligible + simultaneous pathology produces exactly `(phase=FAILED, terminalReason.code=budget_exhausted)` and only persisted `BUDGET_STOP`; no ensemble change/rollback/model call is scheduled.
8. Every strategy action is persisted before effect and is executed once after crash at each recovery cut point.
9. Rollback refuses unknown, cross-run, stale, non-dominant/non-proven checkpoints and any target with a gate in `{fail,error,timeout}`; it never mutates the user checkout and resumes at REVIEWING/required PLANNING, never SIMPLIFYING.
10. Ensemble changes are bounded, cost-eligible, quality-floor-respecting, and target exactly one next review round.
11. Production `CONVERGENCE_CHECK` consumes persisted samples/decisions with the specified total order and preserves accepted B6 anti-fake-DONE and checkpoint-bound clean-round semantics.
12. `BrokerService.restore()` snapshot equals the C2 canonical fold for the same prefix, including duplicate/conflicting-call fixtures.
13. Wall-clock deadline job fires without unrelated activity, survives daemon restart, and appends one replayable evaluation boundary.
14. Existing C3, B6, control-plane, scheduler, store replay, and broker budget tests remain green.
15. `pnpm check` and `pnpm build` pass on Node 24.20.0 with no live/paid provider call.

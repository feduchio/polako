## Why, and what this is not

Review is 78.7% of every token spent and is output-bound at a 5:1 output-to-input ratio. Reviewer
calls today send no `maxTokens` (`src/review/swarm.ts:69-88`).

**This is a tail guard, not a saving.** Observed reviewer completions are 435–1,107 tokens
(finding 43), so a cap at 1500 does not bind in the observed range. Any claim that this item reduces
spend would be false. What it removes is the unbounded case. The recorded trap is that the prompt route
does not work: a clause demanding terseness made output *rise*, 315→349 and 719→895 tokens.

## Deliberate departure from the plan's wording

`docs/PLAN.md` P1.2 specifies that on truncation the execution is persisted as **completed** with
`error: "truncated_output"`, reasoning that `completed: false` plus a non-sticky error would make
`missingAxes` requeue the axis forever. That reasoning is correct about those two options, and it missed
a third that the existing machinery already provides.

**Implemented instead: truncation is a sticky per-model failure.** `reviewAxisWithFallback`'s existing
catch records the failure and falls through to the **next reviewer model** in the same pass
(`src/engine/reviewDrivers.ts:797-826`), and `exhaustedAxes` counts sticky failures toward
`review.maxAxisAttemptsPerRound` (default 6), stopping the run visibly if every model truncates. So the
retry is bounded by machinery that already exists, and no synthetic "completed" row is invented.

Why this is better, stated as the tradeoff it is:

- The plan's option admits an axis that produced **no review** into a completed round, silently. That is
  the same class as P1.1's skip row, but P1.1 has a justification this would not: the skip is a
  deliberate decision not to review, whereas a truncation is a review that failed. Recording a failed
  review as completed loses the distinction convergence depends on.
- Truncation is genuinely per-model: one model's 1,500-token answer may be another's 600. Falling
  through to the next model is the correct response and the driver already does it for every other
  provider failure.
- The cost is that if every model truncates, the run reaches `FAILED` with `providers_unavailable`
  rather than completing with an empty review. With the cap set above the observed range that requires
  reviewers to become dramatically more verbose — in which case stopping and telling the operator to
  raise the cap is right, and silently dropping the review is not.

Recorded as a departure rather than silently satisfied.

## Mandatory clauses

**MC1 — config field.** `review.maxOutputTokens: z.number().int().min(1).default(1500)` in
`ReviewStrategySchema` (`src/domain/config.ts:39-61`). Derivation of 1500: 3× the ~115-token rendered
size of one finding, times a 4-finding allowance, rounded up. It is an estimate, not a measurement.

**MC2 — the cap reaches the provider on every reviewer path.** `runAxisReview` passes it as `maxTokens`
on the `CompletionRequest`; `openaiCompat` maps it to `max_tokens` (`src/providers/openaiCompat.ts:75`).
**Revised in revision 2:** "every path" includes the reviewer-quality benchmark
(`src/review/benchmarkRunner.ts`), which round 1 found uncapped. It is the most token-heavy operator
command in the tool, so leaving it uncapped inverted the item's purpose. It now defaults to the schema
default when no value is threaded, so it can never be uncapped by omission.

**MC3 — truncation is detected, not ignored.** When the response carries `finishReason: "length"`
(`src/broker/types.ts:90`), `runAxisReview` MUST throw rather than parse. A truncated JSON body is
invalid regardless of field order, so parsing it produces either a schema error with a misleading
message or, worse, a partial finding set presented as complete.

**MC4 — the failure is sticky, and the run terminates when it is universal.** The thrown error MUST be
classified sticky by `isStickyReviewSkip`, so the axis falls through to the next model in the same pass.

**Revised in revision 2:** stickiness alone does not bound anything, because production routing excludes
sticky models and a pool smaller than `maxAxisAttemptsPerRound` never reaches the cap. The bound must
therefore come from the wait decision itself: **only a transient exclusion may justify `waiting`.** A
rate limit lifts on its own; a truncation, a 400 and a schema rejection recur unchanged at the same cap.
When every model is excluded and no exclusion is transient, the driver returns `FAILED` with
`providers_unavailable` and a summary **naming `review.maxOutputTokens` and its value**, so the operator
is told what to raise rather than left watching a stalled phase.

**MC5 — the execution records why.** The persisted `ReviewExecution` has `completed: false` and an
`error` naming truncation, through the existing `failExecution` path. No new event type. No synthetic
completed row.

**MC6 — no silent empty review.** A truncated response MUST NOT produce a completed execution with
`findings: []`. This is the defect the item exists to prevent.

**MC7 — the cap does not change P1.1's skip.** A skipped axis makes no provider call, so it cannot
truncate. `isSkippedExecution` continues to match only `error === "no_prior_findings"`, and a truncated
row MUST NOT be treated as a skip.

**MC8a — replay fidelity, added in revision 2.** Detecting truncation live while the rescore harness
forces `finishReason: "stop"` (`src/review/benchmarkRunner.ts`) would turn a truncation into a
completion on replay: a parsable truncated body would rescore as a completed cell. Exported response
packets therefore carry `finishReason`, and replay uses it, defaulting to `"stop"` only for packets
recorded before truncation was detected.

**MC8 — no other behaviour changes.** No change to axis order, reviewer count, exhaustion thresholds,
the ensemble override, the checkout path, or reasoning configuration. The existing
`reasoning: DISABLED_REASONING` on reviewer calls is untouched.

## Round-2 findings, and the scope boundary

**Fixed, because MC2 and MC8a say so and they were violated.**

- **The daemon ignored its own configured cap.** `DaemonService.runReviewBenchmark` called
  `runReviewerBenchmark` without `maxOutputTokens`, so with `[review] maxOutputTokens = 777` every
  benchmark request still carried 1500. Defaulting inside the runner made the benchmark *never
  uncapped*, which is what revision 2 claimed, but it also made a configured value unreachable. AC11.
- **The export side never recorded the live finish reason.** Revision 2 taught replay to *read*
  `finishReason` and never taught the recorder to *write* it, so a live truncation still rescored as a
  completed cell. Both lanes named this. AC12.

**Recorded, not fixed, because they are pre-existing and outside this contract.** Stated explicitly so
the boundary is auditable rather than convenient:

- **Exclusions never expire.** `recentlyRateLimitedReviewModels` has no recency despite its name: an
  excluded model is excluded for the rest of the checkpoint, and only a *completed* execution
  rehabilitates it — which an excluded model cannot produce. So a universal 429 waits forever. That is
  true at base and unchanged by this item: before this change a universal truncation also waited
  forever, and this item converted *that* case to a visible failure without touching the 429 case. The
  GPT lane framed it as "the revision replaced one infinite wait with another"; that framing is wrong on
  the facts, but the underlying defect is real. Recorded in
  `docs/ledger/B-selfhost-remaining.md` as a new finding.
- **Sticky classification is lossy across persistence.** `isStickyReviewSkip` is called with
  `(undefined, execution.error)` from both the exclusion set and `exhaustedAxes`, so its
  `ProviderError.kind` branch is dead in production and `auth`, `not_found` and `context_length` never
  enter the exclusion set at all. `context_length` is deterministic — same prompt, same model, same
  checkpoint — so those axes hang, and neither the exclusion partition nor the attempt cap sees them.
  Both lanes documented it; Grok independently concluded it is not a regression. Recorded as a finding.

## Acceptance criteria

**AC1** The request carries `maxTokens` equal to `review.maxOutputTokens`.

**AC2** Default is 1500, asserted on the schema, not on a literal.

**AC3** A provider returning `finishReason: "length"` produces **no** completed execution for that
axis with that model, and the persisted execution has `completed: false` with an error naming
truncation.

**AC4** With two models where the first truncates and the second answers, the axis completes on the
**second** model in the same tick, and the round advances.

**AC5** A truncated response never yields findings, even when its partial body would have parsed.

**AC6 — rewritten in revision 2.** With a reviewer pool that **models production exclusion**, every
model truncating drives the run to `FAILED` with `providers_unavailable` and a summary containing
`maxOutputTokens`. The revision-1 AC6 is deleted: it used a fixed model list with no exclusion and so
asserted a bound that does not exist in the daemon.

**AC8 — added in revision 2.** A rate limit as the only exclusion still yields `waiting`, not `FAILED`.
Without this the previous fix would trade a hang for a run that dies on a transient 429.

**AC9 — added in revision 2.** Every reviewer call the benchmark issues carries the cap.

**AC10 — added in revision 2.** A response packet carrying `finishReason: "length"` rescores as a
non-completed cell with no findings.

**AC11 — added in revision 3.** A caller-supplied cap is honoured over the schema default, and the
daemon supplies its configured `review.maxOutputTokens`.

**AC12 — added in revision 3.** A live truncated response records `finishReason: "length"` on the
recorded cell, so the exported packet can replay as the truncation it was.

**AC13 — added in revision 3.** A universal **schema** rejection also terminates, with the exact
summary `every reviewer model failed with a non-retryable error`. MC4 says every deterministic
exclusion terminates, not only truncation.

The exact summary is load-bearing: the pre-existing empty-pool path yields the same phase and the same
`providers_unavailable` code, so asserting only phase and code is vacuous — both branches satisfy it.
My first version of AC13 did exactly that and a mutation proved it. This is the third vacuous assertion
of mine that mutation testing caught in two items; see the run record.

**AC6 strengthened in revision 3.** The summary must contain the cap's **value**, not just the knob
name. A mutant dropping the number passed the revision-2 suite, and an operator who is not told the
number does not know what to raise.

**AC7** A truncated execution is not treated as a skip: it does not satisfy `isSkippedExecution`, and it
does not rehabilitate a rate-limited model. (Guards P1.1's MC8a against the new error string.)

## Round 1: recall counted on sites where there was nothing to recall

`scoreAxisRecall` ran `primaryHit` over every cell, `clean` ones included. A `clean` cell has no
planted defect, so a finding there is by definition a false positive — and an axis that only
hallucinated could have been recorded as the sole finder of a pair. This report is what licenses
P3.1 to delete an axis.

Two more in the same round: an axis with no cells vanished from the table, which is exactly the
shape of the partial free-tier run above; and `byModel`, `team` and the discrimination metrics
group without an axis, so widening the schedule silently redefined the fields item 42's figures were
read from.

## Round 2: the slice was a different statistic wearing the aggregate's name

The round-1 fix gave each `byAxis` entry a `QualityMetrics` — computed with `scoreQuality`, the
per-cell aggregate, and printed on the line directly beneath `team (all axes)`, which is
`scoreTeamQuality`, the OR over the two reviewers. The two disagree whenever the reviewers disagree:
one model hitting and the other missing the same cell gives team recall 1/1 and per-cell 1/2. So the
report invited a comparison between two different numbers that shared a name.

AC8 did not catch it because AC8 did not look at the report: it recomputed `scoreQuality` over two
filtered cell arrays and never touched `byAxis`. It passed 50/50 with the defect present. **A
criterion that recomputes the thing it is checking is not observing the artifact.**

The same round found the `ReviewAxisSchema` guard added to `isOracle` in round 1 had no check at
all: widening it to accept any string passed all 971.

## Round 3: two mutants in the seam between the function and the report

Both class (c), both surviving 974 checks. Keying the **report's** table on the axes observed rather
than the configured ones dropped an axis from the persisted artifact — the unit checks observed
`scoreAxisRecall`'s own parameter and nothing observed `buildReport`'s call. And deleting the pair
discrimination from the rendered axis line changed the operator's output with nothing to notice.

The shape is worth carrying: **a well-tested function and a well-tested renderer do not add up to a
tested report.** The call site between them is its own surface.

## Round 5: the second lane attacked the result rather than recomputing it

The entry gate had already verified the numbers, so the Grok lane went after the thing that makes
them suspicious: **a metric that reports the same value for every axis.** It recomputed the
pair-level hitter sets from the CAS cells without going through `scoreAxisRecall`, and ran two
counterfactuals — counting clean-site primary hits, and counting any mutant finding at all — both of
which still yield no unique pair. It then constructed the positive case through
`runReviewerBenchmark` rather than the unit function: a 36-cell run where only `adversarial` finds
the planted defect reports `byAxis.adversarial.uniqueHits === 1`, and when `correctness` also finds
it all three return to 0.

So `uniqueHits: 0` is the correct answer for this data, not a fold that collapsed. It also killed
the mutant that would produce that answer from any input — adding every configured axis as a hitter
— against AC5 and AC8a.

It additionally confirmed that the live cells carried P1.2's output cap (`maxTokens === 1500`) and a
distinct production prompt per scheduled axis, which is the interaction between the two items that
